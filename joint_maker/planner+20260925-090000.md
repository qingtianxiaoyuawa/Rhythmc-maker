# RhythMC Maker 播放流动参数检查记录

- 时间：2026-09-25 09:00:00 +08:00
- 工作类型：检查播放时音符流动、缓动、流速与时钟参数
- 结论：当前播放为基于单调时钟的线性、分段移动，没有专门缓动或客户端平滑插值。

## 当前参数

- 播放平台：`(200, 65, 0)`
- 播放/判定平面：`Z = -2`
- 音符预加载距离：`25.0` 格
- 显示刷新间隔：`1` tick，即理论 `20 TPS`
- 基础流速：`5.0` 格/拍
- 玩家速度倍率：`0.1..5.0`，默认 `1.0`
- 实际流速：`5.0 × playerSpeed` 格/拍
- 播放起始延迟：`0` tick
- 时间源：`System.nanoTime()`
- Display 插值：`teleportDuration = 0`、`interpolationDuration = 0`

## 当前移动模型

```text
距离 = (音符时间 - 播放起始时间) × BPM / 60 × 5.0 × playerSpeed
相对距离 = 音符距离 - 当前播放距离
displayZ = -2 - 相对距离
```

音符每个服务端 tick 直接更新 BlockDisplay 坐标，抵达 `Z = -2` 后下一 tick 回收。没有 ease-in、ease-out、lerp、smoothstep、cubic interpolation 或基于 speedEvents 的动态速度曲线。

## 影响与风险

1. 20 TPS 更新导致客户端高帧率下可能出现阶梯感或轻微跳动。
2. 当前播放代码只使用固定基础流速和 `playerSpeed`，没有完整接入 RhythMC 3.0 的动态 `speedEvents` 语义。
3. 音符位置按时间线性换算，没有按轨道距离曲线积分。
4. 音频由客户端 `ffplay.exe` 单独启动；源码层面需要实际游戏试听才能确认音画同步。
5. 上一条编译记录明确未完成游戏内实际按键和试听验证。

## 后续建议

- 第一优先级：实际游戏试听，记录不同 FPS、BPM、playerSpeed 下的音画同步和视觉平滑度。
- 第二优先级：如果保留服务端 BlockDisplay，研究启用合理的实体插值，而不是简单把插值时间设为 0；插值时长必须与 tick 更新周期和速度变化协调。
- 第三优先级：抽象 `distanceAt(time)`，接入 3.0 的 speedEvents，使用分段积分计算位置。
- 第四优先级：明确“制谱器预览播放”与“正式谱面 3.0 播放”的坐标、速度和判定语义，避免两套模型不一致。
