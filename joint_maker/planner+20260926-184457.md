# 本轮规划记录

## 用户问题
确认 RhythMC 3.0 源码是否支持在标准 `.rmcc` 文件的 `beat` 字段中写入分数，并评估在不修改导出文件格式的前提下如何解决无限小数精度问题。

## 源码确认
本地 RhythMC 3.0/Reborn 源码位置：
`F:\b晴天小雨awa\RhythMC\rhythmc maker\analysis\RhythMC-Reborn-master`

关键证据：
- `File/Deserializers/NoteDeserializer.java:34` 使用 `double beat = object.getDoubleValue("beat")`。
- `Game/Format/Note.java:5` 的 `Note` record 将 beat 定义为 `double beat`。
- BPM、Effect、NumEvent 等节拍字段同样按 `double` 读取。

## 结论
- 标准 `.rmcc` 的 `beat` 字段支持 JSON 数字，例如 `10.333333333333334`、`56.5`。
- 不支持把 `beat` 写成 `31/3`、`1/7` 等分数文本；`31/3` 也不是合法 JSON 数字，不能被当前 3.0 的 `getDoubleValue("beat")` 作为标准 beat 读取。
- 不能把 `beat` 改成字符串分数，否则会偏离当前 3.0 文件格式和运行时数据模型。
- Reborn 的反序列化器只读取已知字段，音符上的未知附加字段不会被当前解析逻辑使用；但用户已要求导出文件保持标准格式，因此不应把额外字段作为标准 `.rmcc` 解决方案。

## 在标准格式不变下的正确方案
1. 导出端不再从 `time` 反算 beat，直接写内部 `note.beat`。
2. 导入端读取 `sourceBeat` 后直接赋值给 `note.beat`，只单向计算 `note.time`，禁止 `beat -> time -> beat` 覆盖原始 beat。
3. 使用足够精确、可被 JSON 解析器往返还原的十进制 double 表示。Gson 的普通 double 输出应保持 round-trip 数值，不要主动截断小数位。
4. 3.0 标准文件只保存 double 近似值；Maker 内部的 `.rmcd` 或独立编辑器数据保存精确分子/分母、BigDecimal 或原始十进制字符串。
5. 如果需要 Maker 自己重新打开时数学无损，必须同时保留 Maker 工程文件/侧车数据；仅凭标准 `.rmcc` 无法恢复导出前未写入的精确分数。

## 重要边界
- 这能保证“同一个 double beat 导出再导入不发生额外漂移”，但不能让标准 `.rmcc` 的 double 字段变成数学意义上的无限精确分数。
- 若原始位置来自 `slot / divisionsPerChunk`，Maker 应在内部保存精确网格参数，导出时计算一次 double；不要导出前先经过 time。
- 3.0 运行时本身也是 double beat，因此 Maker 不应导出一个 3.0 无法读取的分数格式。

## 建议验收
- `10.333333333333334`、`10.142857142857142`、`25.083333333333332` 导出后重新导入，比较 `Double.doubleToLongBits` 或严格数值是否一致。
- 变 BPM 和非零 offset 下，beat 不变，只有 time 变化。
- 不带 Maker 私有数据的标准 `.rmcc` 仍按 3.0 规则正常导入。

## 本轮结论
标准 `.rmcc` 不能写入真正的分数 beat；可行修复不是改变文件格式，而是取消 beat/time 往返转换、直接保留标准 double beat，并把数学精确值放在 Maker 自己的 `.rmcd` 或侧车工程数据中。
