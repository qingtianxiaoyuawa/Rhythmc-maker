# RhythMC Maker 大谱面交互卡顿深层修复规划

- 日期：2026-10-03 15:19:16（Asia/Shanghai）
- 规划身份：Planner；本轮不修改源码、不编译、不测试、不部署。
- 当前实现基线：`1.5.26`。

## 用户现象

1. 播放中的流动音符本身流畅，但触发保存或挖掘方块时音符明显卡顿。
2. 导入一张约 6 分钟的完整 2.0 谱面后，几乎所有操作都出现明显延迟。
3. 需要从根层修复，不改变既有播放、判定音、谱面坐标和时间逻辑。

## 已定位的共同根因

### A. 交互事件重复解析整张谱面

- `RhythmcMaker.java:262`、`RhythmcMaker.java:305` 的放置/挖掘路径都会调用 `loadActiveChart(...)`。
- `RhythmcMaker.java:786-790` 的 `loadActiveChart(...)` 每次都执行 `ChartStorage.find(...)`，即重新读取并解析完整 JSON。
- 大谱面操作一次方块，就可能在服务端主线程重新构造数千个音符、特效和轨道对象；这会直接阻塞 Tick，并表现为音符移动卡顿和操作响应延迟。

### B. 保存仍在服务端 Tick 线程同步完成

- `RhythmcMaker.java:247-254` 的自动保存在服务端 Tick 中调用 `saveActiveChart(...)`。
- `RhythmcMaker.java:772-773` 会再次读取谱面后执行保存。
- `ChartStorage.java:423-430` 的 `update(...)` 同时写 manifest 和 `.rmcc` 两份大 JSON。
- `ChartStorage.java:546-552` 使用完整对象序列化；`ChartStorage.java:570-587` 又进行 JSON 解析、写临时文件、再次读取临时文件解析，并复制 `.bak`。
- 因此一次保存包含重复序列化、重复解析、磁盘写入和备份复制，全部可能阻塞服务端 Tick。

### C. 2.0 导入把 CPU 和磁盘工作放在服务端主线程

- `ImportChartScreen.java:177-180` 将 `ClientChartAccess.importRhythmc3/importRhythmc2` 放入 `client.getServer().execute(...)`。
- 大谱面导入的 JSON 解析、音符转换、时间换算、对象分配、文件写入以及场景初始化会连续占用服务端线程。
- 导入结束后，如果活动谱面没有进入稳定的内存缓存，后续交互还会反复触发 A、B 两条阻塞链。

## 深层修复原则

### 1. 建立运行时谱面缓存，磁盘不再作为交互查询源

- 新增按服务器/谱面 ID 管理的运行时状态，进入谱面时只加载一次。
- `loadActiveChart(...)` 改为内存缓存查询；只有进入谱面、主动重新加载或缓存失效时才访问磁盘。
- 放置、挖掘、轨道调整、特效编辑、播放启动均操作同一个活动谱面对象或运行时状态。
- 活动谱面切换时先停止旧任务，再切换缓存引用，避免旧谱面结果覆盖新谱面。
- 播放逻辑继续读取现有谱面数据和时间字段，不改变播放计算、判定音和坐标映射。

### 2. 用“脏标记 + 修订号”替代无条件保存

- 每次谱面变更只更新内存对象并递增 revision，标记 dirty。
- 自动保存只处理 dirty 谱面；无修改时不得再次序列化和写盘。
- 保存任务携带 revision；写盘完成后仅当当前 revision 未变化时清除 dirty，避免旧保存结果覆盖新编辑。
- 保存按钮改为提交保存请求并显示状态，不在按钮回调中等待完整 JSON 写盘。
- 退出、切换谱面和显式保存仍保留原有语义，但改成等待/排队保存，不改变用户可见功能。

### 3. 保存采用后台单写入器，主线程只提交轻量快照

- 使用单独的 chart persistence executor，保证同一谱面写入顺序稳定，避免并发写同一文件。
- 主线程不得执行 `Gson.toJson`、完整 JSON 校验、`Files.copy`、`Files.writeString` 或整谱面 `find`。
- 快照必须是线程安全的：优先采用不可变快照或分块/写时复制结构，不能让后台线程直接遍历正在被主线程修改的 `ChartManifest`。
- 不能简单地在主线程对整个大列表做一次深拷贝后声称异步；深拷贝本身也会造成卡顿。
- 推荐将音符按固定数量分块保存，编辑只替换受影响块；后台写入由 revision 对应的稳定快照组成。
- 如暂时无法实施分块快照，第一阶段至少使用增量操作日志/WAL 记录新增、删除和字段修改，后台定期生成完整检查点；恢复时先加载检查点再回放日志。

### 4. 降低保存链路的重复工作

- 保留原子替换和 `.bak` 恢复机制，但移除“生成后写入、再读回并完整解析一次”的重复校验路径。
- 保存前在内存对象层执行字段和数值校验；序列化结果只做必要的最终完整性检查。
- manifest 与 `.rmcc` 不应无条件同时写入完整音符数据；先确认两者的兼容用途，避免同一大谱面被重复序列化。
- 若必须保留双文件格式，建议一个作为元数据索引、另一个作为完整谱面文档，避免两个文件都包含完整 notes。
- 大谱面内部存储可使用紧凑 JSON 或流式写入，但必须保持读取兼容，不改变播放逻辑。

### 5. 导入拆成“后台转换 + 主线程分批提交”

- 2.0 原始文件读取、JSON 解析、音符转换、BPM/timing 计算、格式校验和音频文件复制放入导入 executor。
- 主线程只接收已经完成的导入结果，并分批执行必须由 Minecraft 世界线程完成的场景/区块操作。
- 每 Tick 设置场景提交预算，禁止一次导入同步创建全部场景、区块和装饰方块。
- 导入期间显示阶段进度：读取、转换、保存、场景提交；禁止用户误以为游戏卡死而重复操作。
- 导入完成后一次性发布活动谱面缓存，后续交互不能再次从磁盘解析整张 2.0 谱面。
- 不修改导入后的 beat、time、BPM、轨道坐标和播放数据语义。

## Spark 结合方案

Spark 只用于确认运行时热点，不作为唯一依据。实现方应分别采集以下场景：

1. 未导入大谱面时的空闲制谱器基线。
2. 导入 6 分钟 2.0 谱面后的空闲状态。
3. 单次保存期间。
4. 单次挖掘音符方块期间。
5. 连续放置/挖掘数次期间。

重点观察服务端主线程是否出现以下栈：

- `ChartStorage.find` / `Gson.fromJson`。
- `ChartStorage.update` / `Gson.toJson`。
- `Files.readString`、`Files.writeString`、`Files.copy`。
- `ChartStorage.importRhythmc2` / `importRhythmc3`。
- 场景安装、区块修改和 `setBlockState` 批量操作。
- `processPlaybackSessions` 是否只是被上述阻塞拖延，而不是自身算法退化。

建议使用 Spark profiler 记录服务端线程火焰图，并同步记录一次保存/挖掘操作的开始时间、结束时间、Tick 耗时和队列长度。若 Spark 未捕获短时尖峰，补充带统一标签的边界计时，不记录每个音符的高频日志。

## 禁止的表层修复

- 不得只把 `ChartStorage.find` 的异常吞掉。
- 不得只提高自动保存间隔来掩盖阻塞。
- 不得只把保存调用扔进线程池，却让后台线程直接读取/遍历正在修改的 `ChartManifest`。
- 不得通过减少播放音符、降低播放刷新率或改变播放速度来掩盖卡顿。
- 不得删除谱面内容、减少 2.0 音符或改变时间轴逻辑。

## 实施顺序

1. 先加入 Spark/边界计时，确认保存、挖掘和导入的主线程热点。
2. 建立活动谱面运行时缓存，移除交互事件中的重复磁盘解析。
3. 加入 dirty/revision 状态，阻止无变化自动保存。
4. 实现线程安全的不可变/分块快照和单写入器。
5. 将 2.0 导入转换与磁盘操作后台化，世界修改分 Tick 分批提交。
6. 保留原子替换、备份恢复和损坏文件隔离。
7. 进行大谱面、保存、挖掘、导入和播放并行回归。

## 验收标准

- 导入 6 分钟完整 2.0 谱面后，空闲、移动、打开菜单、挖掘和放置操作无明显输入延迟。
- 保存操作不再导致音符移动停顿；保存期间服务端 Tick 不出现长阻塞。
- 挖掘/放置只更新内存缓存和必要的增量数据，不重新解析完整谱面。
- 播放的音频、判定音、音符位置、速度、时间轴和特效逻辑保持原行为。
- 强制中断保存时，旧有效文件仍可恢复，新文件不会是半截 JSON。
- Spark 火焰图中，正常交互路径不再以 `ChartStorage.find`、`Gson.fromJson`、`Gson.toJson` 或文件复制作为主线程主要热点。
- 回归记录必须给出：谱面音符数量、导入耗时、保存耗时、单次挖掘耗时、主线程 Tick 峰值和播放同步结果。
