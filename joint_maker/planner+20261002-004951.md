# 滚动播放功能边界修订：仅音乐与判定音

- 日期：2026-10-02
- 用户确认：滚动播放不触发特效，仅触发音乐和判定音播放。
- 关联记录：`planner+20261002-003820.md`。
- Planner 边界：仅规划和修订诊断，不修改源码、不编译、不测试、不部署。

## 功能边界

滚动播放应只负责三件事：

1. 播放谱面音频。
2. 根据谱面时间推进判定音。
3. 在客户端渲染滚动白框/当前播放位置。

滚动播放明确不负责：

- 特效事件：TITLE、MESSAGE、TEXT_DISPLAY、WEATHER、TIME、GLOW_COLOR、HIDE_NOTES 等。
- BlockDisplay 音符实体创建、移动、发光、回收。
- 正式播放场景传送和返回。
- 世界状态改变、天气/时间改变、药水代理或场景切换。
- 特效时间轴事件的服务端执行。

正式播放继续保留完整的音符实体、特效和世界状态逻辑；本次边界只约束 scroll 模式。

## 对当前问题的进一步判断

当前服务端代码虽然在 `session.formal == false` 时跳过正式音符 Display 分支和特效分支，但仍创建完整 `PlaybackSession`，并在每个 Server Tick 中执行 scroll 分支：

- 推进 `nextNoteIndex`。
- 检查所有 `noteTime <= songTime` 的音符。
- 为每个到时音符调用 `playHitSound(...)`。

因此问题不是“滚动播放触发了特效”，而是**滚动播放复用了正式播放会话的大量准备和生命周期，只是运行时跳过了部分输出**。它仍可能承担不必要的成本：

- 复制并排序完整 notes/effects 列表。
- 准备每条轨道的 `TrackPlayback`。
- 建立完整 `notesById`、`noteTimes` 等映射。
- 复制/排序 effects，尽管 scroll 模式不执行 effects。
- 创建完整 `PlaybackDistance` 和正式播放相关状态。
- 在 Server Tick 中维持服务端 session 和停止清理路径。

这与“滚动播放前无卡顿、播放中操作延迟、结束后仍有延迟”的现象相符：滚动模式启动了不必要的服务端播放工作，集成服务器 Tick 与制谱器输入共享进程资源。

## 推荐架构：轻量 ScrollPlaybackSession

不建议继续把 scroll 模式作为 `PlaybackSession.formal = false` 的分支长期维护。应明确拆出轻量会话，至少拥有以下状态：

- 玩家 UUID。
- 谱面 ID/必要的谱面时间索引。
- 起始 Beat/起始秒数。
- 共同播放开始单调时间。
- 播放倍率。
- 判定音所需的音符时间数组和 `nextNoteIndex`。
- 判定音去重状态或最后已处理音符索引。
- 播放结束时间。

轻量会话不应拥有：

- `DisplayEntity` 映射和对象池。
- glow team。
- effects 列表或 effect 索引。
- TrackPlayback 轨道姿态和正式实体位置计算。
- 特效状态集合。
- 玩家传送/返回状态。
- 世界状态修改器。

## 判定音处理要求

滚动模式需要保留判定音，因此不能简单改成完全客户端本地白框播放后丢弃服务端会话。推荐保留一个最小服务端/客户端判定音链路，但只传递和处理必要信息。

### 优先方案：客户端判定音

如果判定音只需本地玩家听到，优先考虑把判定音也放到客户端：

- 客户端使用与音频相同的播放时间锚点和音符时间索引。
- 到达音符时间时在客户端播放对应判定音。
- 不创建服务端播放会话，不执行 Server Tick 音符扫描。
- 不产生服务端声音数据包和命令往返延迟。

该方案最有利于解决集成服务器操作响应问题，但需要确认判定音当前是否依赖服务端世界声音、服务端音量配置、多人可见性或服务器权威判定。

### 保守方案：轻量服务端判定音会话

如果判定音必须由服务端发出：

- 只建立 `ScrollJudgementSession`，不复用完整 `PlaybackSession`。
- 启动时只预计算有效音符的判定时间和音符类型，不复制 effects、不准备轨道姿态、不计算显示距离。
- 每 Tick 只推进一个有序时间索引。
- 一次 Tick 处理多个到时音符时设置明确预算，并记录积压数量；不能无限 while 扫描造成长 Tick。
- 通过 `world.playSound(player, ...)` 或等价的单玩家声音发送路径，只向目标玩家发送判定音，避免广播给无关玩家。
- 判定音事件处理完后立即丢弃已处理数据，不保留正式播放的实体/特效状态。

## 客户端白框与轻量会话同步

- 音频、白框和判定音必须使用同一个 `startSeconds`、`startNanos` 和 `playbackRate`。
- 白框不能在音频进程真正启动前单独开始计时。
- 轻量服务端判定音会话不能再使用一个与客户端音频启动时刻无关的固定延迟起点。
- 若服务端和客户端仍有通信延迟，应发送明确的目标开始时间/同步序号，而不是依赖命令到达时间。
- 白框位置继续使用统一的 `PlaybackCoordinates`/Beat-to-world-Z 映射，不能恢复独立线性公式。

## 播放结束清理

滚动播放结束时只需要清理：

- ffplay 进程。
- 客户端白框播放状态。
- 客户端播放时钟和缓存的坐标转换状态。
- 轻量判定音 session 或客户端音符时间索引。
- 未发送/未处理的停止同步状态。

滚动播放结束不得执行：

- Display 实体全量扫描。
- glow team 清理。
- 正式播放玩家传送回原位置。
- 特效状态回滚。
- 与滚动模式无关的世界清理。

如果为了兼容旧 session 仍需要 `stopPlayback`，应先按 session 类型分流，轻量 scroll session 走 O(1) 清理路径，不能进入正式播放的实体清理路径。

## 诊断采样重点

实现方应分别记录：

- scroll session 创建耗时、音符数量和预计算耗时。
- 每 Tick 判定音处理数量、耗时和积压。
- 音频进程实际启动时间、白框时钟起点和判定音 session 起点。
- 播放结束时音频退出、客户端清理、服务端 session 移除的时间差。
- 播放前、播放中、播放后的 Client Tick/Server Tick p95 和最大耗时。
- 是否仍执行 `effects` 排序、`TrackPlayback.prepare`、Display 扫描或 glow team 操作。

## 验收标准

### 功能

- 滚动播放有音乐。
- 滚动播放有与音符时间对应的判定音。
- 滚动播放不触发任何特效。
- 滚动播放不创建或移动正式音符 Display 实体。
- 滚动播放不改变天气、时间、发光、场景或玩家传送状态。
- 正式播放的音符、特效和世界逻辑不受影响。

### 性能

- 滚动播放不再构造完整正式播放会话。
- 播放期间制谱器操作响应接近未播放状态；不能只以 FPS 稳定作为通过条件。
- 播放结束后不存在残留 session、音频进程、清理任务或命令积压。
- 不执行与音乐/判定音无关的 effects、实体、轨道姿态和世界清理工作。

### 同步

- 音频、白框和判定音共用同一播放起点和播放倍率。
- 起始 Chunk、BPM 分段、offset 和 speed/坐标映射保持一致。
- 判定音不因服务端 Tick 偶发延迟而无限追赶造成长 Tick；若发生积压，有明确策略和日志。

## 交给实现方的任务清单

1. 将当前 scroll 分支从完整 `PlaybackSession` 中拆出，设计轻量 `ScrollJudgementSession` 或客户端判定音状态。
2. 确认判定音是否必须服务端发出；若仅本地玩家需要，优先迁移到客户端。
3. 删除 scroll 模式对 effects、Display、glow、TrackPlayback 和世界状态逻辑的依赖。
4. 统一音乐、白框和判定音的时间锚点与播放倍率。
5. 为播放结束设置独立轻量清理路径，不进入正式播放清理逻辑。
6. 加入低侵入性能采样，比较播放前/中/后的 Tick 与输入响应延迟。
7. 编译、运行和部署由执行方完成；Planner 不执行工程修改。

## 本轮结论

滚动播放的正确模型应是：**客户端音乐 + 白框位置 + 轻量判定音时间线**，而不是“正式播放会话关闭实体分支后的简化版”。既然滚动播放不触发特效，就应从根本上移除 effects、实体、轨道姿态、发光队伍和世界状态处理，只保留音频和判定音所需的最小时间索引。这样才能同时解决播放期间和播放结束后的制谱器响应延迟，并降低音频/白框/判定音的同步复杂度。
