# 本轮规划记录

## 用户问题
导出谱面时对每个 beat 进行计算转换，遇到无限小数会保存近似值；导入时把近似值当作准确值，导致音符对应的谱面位置发生偏移。

## 已确认的代码链路
- `src/main/java/cn/frkovo/rhythmcmaker/chart/Rhythmc3Exporter.java` 的 `exportBeat(...)` 当前优先使用 `note.time` 调用 `timing.secondsToBeat(note.time)`，导出时不是直接写入编辑器中的 `note.beat`。
- 同一导出文件把计算结果写入 3.0 `.rmcc` 的 `tracks[].notes[].beat`。
- `src/main/java/cn/frkovo/rhythmcmaker/chart/ChartStorage.java` 的 3.0 导入流程先执行 `note.time = timing.beatToSeconds(sourceBeat)`，随后执行 `note.beat = timing.secondsToBeat(note.time)`，再次进行一次浮点往返。
- 音符编辑坐标 `note.z` 根据 beat 映射；因此 beat 的微小误差会表现为音符在轨道中的小数位置或相邻位置偏差。

## 根因判断
1. 3.0 `.rmcc` 中的标准 `beat` 是运行时谱面时间轴字段，不应通过 `time` 反推。
2. `double` 可以近似表示无限小数，但不能保证保存任意分数的数学精确值。
3. 当前存在 `beat -> seconds -> beat` 的无必要往返，放大了 JSON 十进制序列化与浮点误差。
4. 若只拿已经四舍五入后的 3.0 `beat`，无法普遍恢复原始的 `1/3`、`1/7` 等精确分数；必须在导出时额外保存编辑器的精确信息。

## 推荐方案
### A. 立即修复标准字段的权威方向
- 导出 3.0 时，标准 `tracks[].notes[].beat` 直接写 `note.beat`。
- `exportBeat(...)` 不再默认从 `note.time` 反算；只有 `note.beat` 非法且确实没有 beat 数据时，才允许用 time 作为兼容回退。
- 导入 3.0 时，`sourceBeat` 直接赋给 `note.beat`。
- 导入后只计算 `note.time` 作为播放缓存，不再执行 `beat -> time -> beat` 并覆盖原始 `sourceBeat`。
- `note.z` 始终由导入得到的权威 beat 计算；不要由 time 计算 z。
- offset 只在播放时参与有效时间，不修改存储 beat。

### B. 增加 Maker 精确扩展字段
标准 RhythMC 3.0 仍保留正常 `beat`，同时在 Maker 导出中增加可被 3.0 忽略的扩展字段，例如：
```json
{
  "beat": 10.333333333333334,
  "makerBeatNumerator": 31,
  "makerBeatDenominator": 3
}
```
或使用：
```json
{
  "beat": 10.333333333333334,
  "makerBeatExact": "31/3"
}
```
- 优先推荐 `makerBeatExact` 字符串或 numerator/denominator 两个整数；不要依赖浮点字段保存精确值。
- 导入 Maker 自己导出的文件时优先读取精确扩展字段，再生成 `double beat` 和 `z`。
- 导入没有扩展字段的外部 3.0 谱面时，使用标准 `beat` 原值，不做自动量化或猜测。
- 扩展字段放在单音符对象上最稳妥；也可在 `meta` 中声明扩展格式版本。

### C. 内部编辑模型改为“精确节拍 + 播放缓存”
长期建议将 `ChartManifest.Note` 的时间核心拆为：
- `exactBeat`：`BigDecimal` 或有理数 numerator/denominator，作为编辑与导出的权威值；
- `beat`：用于兼容现有 3.0/Gson 逻辑的 double 派生值；
- `time`：根据 BPM 计算出的播放缓存，不参与反向覆盖 exactBeat。

如果 Maker 的音符来源始终是“Chunk 内格位”，可以保存：
```text
beat = chunkIndex + slotIndex / divisionsPerChunk
```
并在导出时约分为整数分子/分母。对于外部 3.0 输入的任意十进制 beat，则保存其原始十进制字符串或 BigDecimal，不能擅自认为它是某个简单分数。

## 不推荐的方案
- 只把 `double` 改成 `float`：精度会更差。
- 导入时按 `1e-8` 或 `1e-6` 自动四舍五入：可能把合法的非网格 beat 改错。
- 通过 `secondsToBeat(beatToSeconds(x))` 修复精度：这是同一问题的重复往返。
- 只提高 JSON 小数位数：能减少显示误差，但不能恢复已经丢失的数学信息。
- 只依赖 `time` 作为唯一坐标：BPM 变化、offset 和毫秒取整都可能造成位置漂移。

## 建议实现顺序
1. 先修正导出：`beat` 直接来自 `note.beat`，保留 time 仅作播放数据。
2. 再修正 3.0 导入：`sourceBeat` 直接写入 `note.beat`，只单向计算 `note.time`。
3. 增加 `makerBeatExact` 或 numerator/denominator 扩展字段，并在 Maker 自导出的文件中写入。
4. 导入时优先读取扩展字段；无扩展时兼容标准 beat 原值。
5. 增加导入-导出-再导入的数值测试，至少覆盖 `56.5`、`10+1/3`、`10+1/7`、`25+1/12`、变 BPM 和 offset 不为 0 的情况。
6. 检查 `note.z`、Chunk 显示位置、播放时间三者是否分别由 beat、编辑映射、timing 单向派生。

## 验收标准
- Maker 导出的音符再次导入后，精确 beat 与原编辑数据一致。
- 变 BPM 不会改变 beat，只影响 time 缓存。
- offset 改变播放起点，不改变音符空间位置。
- 没有 Maker 扩展字段的原生 3.0 谱面仍可正常导入。
- 外部 3.0 谱面中的合法小数 beat 不会被自动量化为整数或 Chunk 网格。
- 对存在无限小数的网格位置，重导入后不会因反算 time 导致位置漂移。

## 本轮结论
核心原则是：`beat` 是谱面位置和事件顺序的唯一权威数据；`time` 只在播放边界生成；需要数学无损时，在标准 3.0 beat 外增加 Maker 私有精确字段。当前仅完成分析与规划，没有修改源码、编译或部署。
