## 总体结论
当前 Maker 与 3.0 的谱面时钟、轨道事件、音符轨迹、特效事件并非完全同一条运行链路，因此“Maker 中看起来正确”不能直接保证在 RhythMC 3.0 实际游玩中逐帧一致。已确认或高度可疑的视觉差异主要集中在：

1. Maker 正式播放额外使用 `PLAYBACK_FLOW_MULTIPLIER = 5.0`，而参考 3.0 的 `ChartUtils.getDistance()` 只使用速度积分乘玩家速度，未见同等 5 倍倍率。
2. Maker 正式播放把音符放到独立的预览平台/世界坐标，并采用自己的 `PLAYBACK_FRAME_Z`、消失边界、预加载和服务端 tick 更新；3.0 使用 `screenCenterLoc`、`TrackObject.currentDistance` 和 NoteType 的近远裁剪。绝对场景位置可以不同，但相对判定线距离、进入/离开视锥和命中瞬间必须一致，目前没有统一契约。
3. Maker 音符姿态通过 `displayPosition()` 的局部坐标、轨道旋转和 Z 反向组合计算；3.0 的 `NoteObject.computeRenderState()` 使用明确的 Z 轴方向、旋转顺序 `Z -> Y -> X` 后再叠加轨道平移。两者结构相近，但没有共享矩阵/坐标适配器，存在旋转、非均匀缩放和轨道变换叠加差异风险。
4. Maker 轨道数值评估与 3.0 都使用速度事件梯形积分和缓动，但 Maker 自己复制了一套 easing/事件边界代码；只要 easing 编号映射、空窗默认值、事件端点处理或无序/重叠事件处理有一处不同，就会导致长谱面逐渐漂移。
5. Maker 音频/播放时钟是 `System.nanoTime()` 驱动的 `songTime`，每 tick 计算 Beat；3.0 由 `TimingManager` 以毫秒、BPM 表和 offset 换算 Beat，再驱动 `GameInstance` 的 `level.update(curBeat, elapsedMillis)`。Maker 播放时当前音频、音符命中音、特效和位置没有被同一个可 seek 的音频时钟直接锚定；拖动/暂停/长谱面下可能出现累计偏移。
6. Maker 的滚动播放明确只触发判定音，并仅复用部分特效预览逻辑；它不是 3.0 正式游玩链路，不应作为导出兼容性的证据。
7. 2.0 特效转换和 Maker 文本播放虽已补齐 `location/contents`、`position/text/rotation/scale` 等字段，但 3.0 的 TextDisplay 是持久对象+矩阵变换+轨道同步；Maker 直接创建/更新服务器 TextDisplay。若事件 duration、相对场景原点、文本初始属性、插值、轨道同步和移除时机不统一，文本、全息和动画会出现位置/时长/淡入淡出差异。
8. 音符外观还受 3.0 `noteSkin`/`GameUtils.getNoteSkinFromType()` 和 Maker `blockStateForType()` 两套映射控制。即使时间和位置一致，方块材质、发光、HOLD 分段、LOOK/TAP 的视觉形态也可能不同。

## 已核对的播放链路

### Maker
- 服务端 tick 入口在 `RhythmcMaker.processPlaybackSessions()`。
- 正式播放：以 `startSeconds + elapsedNanoSeconds * rate` 计算歌曲时间；按 `ChartTiming` 转 Beat；处理特效；维护 BlockDisplay 音符池；按 note time 到点播放判定音。
- 正式播放的音符位置由 `PlaybackSession.relativeDistance()`、`displayPosition()`、`applyNotePose()` 计算；实体在预览平台附近生成，达到命中时间后回收并播放判定音。
- 特效按 `effectSeconds <= songTime` 顺序触发；文本事件通过 `TEXT_DISPLAY*`/`HOLOGRAM` 分支创建、更新和清理。
- 滚动播放使用 `ScrollJudgementSession`，只推进判定音和最多部分效果会话；不等价于 3.0 正式游玩。
- 关闭播放时清理显示实体、文本显示、队伍和状态效果，并将正式播放玩家传回原位置。

### 3.0 参考实现
- `TimingManager` 读取 BPM 表和毫秒 offset，负责 `calcBeat()`、`beatToMillis()`；`GameInstance` 以 elapsedMillis 驱动 `level.update(curBeat, elapsedMillis)`。
- `TrackObject.update()` 先更新当前距离和轨道变换，再更新 NoteObject 与判定；`getDistance()` 调用 `ChartUtils.getDistance(speedEvents, beat, playerSpeed)`。
- `NoteObject.update()` 使用 `distance - track.currentDistance + note.posZ * track.zScale` 得到相对距离；按 NoteType 的 near/far 窗口显示/隐藏；姿态由轨道缩放、轨道旋转、平移及音符自身姿态组成。
- TextDisplay 通过 `TextDisplayManager`/`GpTextDisplay` 持久化对象；矩阵组合为 `translate -> rotateXYZ -> scale`，再由 `TEXT_DISPLAY_EFFECT` 或 `TEXT_DISPLAY_SYNC_TRACK` 更新；duration 到期由 EffectManager 清理。
- 游戏结束/退出时停止声音并清理显示对象。

## 差异判定

### A. 已确认或应按高风险处理的差异

#### A1. 速度积分尺度不统一
- Maker：`PlaybackCoordinates.distanceAtBeat()` 和 `distanceBetweenBeats()` 额外乘 `5.0`。
- 3.0 参考：`ChartUtils.getDistance()` 仅对速度积分结果乘 `playerSpeed`。
- 影响：音符接近速度、屏幕上可见时长、命中线前移动距离、轨道 Z 变换视觉节奏都可能整体放大约 5 倍。即使 Maker 自己内部音频与白框同步，导出到 3.0 后也可能出现“Maker 看到的移动距离/速度”和实际游玩不同。
- 处理优先级：P0。必须先确认 5.0 是否是 Maker 场景单位换算，而不是误加速；不能直接删除，需用同一测试谱面在两端测量“Beat 0、命中 Beat、Beat+N 的世界 Z/屏幕像素距离”。

#### A2. 时钟实现不是统一的 ChartTiming 协议
- Maker 自己以纳秒实时差推进 `songTime`；3.0 以毫秒 elapsed + TimingManager 推进 Beat。
- Maker `ChartTiming` 的 beat/second 换算在数学上与 3.0 类似，但端点精度、offset 的加减方向、负时间和毫秒四舍五入策略可能不同。
- 影响：offset、BPM 变化点、暂停/恢复、seek、播放速率、长曲累计误差，以及音频播放设备延迟都可能使音符、轨道、特效错位。
- 处理优先级：P0。以 `ChartTiming` 为唯一主时钟，所有音符、轨道、特效和 seek 使用 beat/毫秒双向映射；音频播放必须可按目标毫秒 seek，不能只移动 UI 指针。

#### A3. 坐标/矩阵实现分叉
- Maker 的 `displayPosition()` 与 3.0 `NoteObject.computeRenderState()` 都包含局部坐标、轨道旋转、轨道平移、Z 反向，但并未共享同一套坐标适配器。
- 影响：轨道旋转、非均匀缩放、音符旋转/缩放、TextDisplay 和 BlockDisplay 的相对基点可能产生可见差异，尤其是 Y 中心、Z 正负方向和旋转顺序。
- 处理优先级：P0/P1。抽象并固定 `ChartRenderTransform`：输入 `(note local, track pose, relative distance, chart origin)`，输出世界位置、Quaternion/矩阵、scale；Maker 与导出格式均通过同一契约回归。

#### A4. 音符窗口和实体渲染策略不同
- Maker 以 `PLAYBACK_APPROACH_DISTANCE`、`PLAYBACK_DISAPPEAR_Z`、`PLAYBACK_FRAME_Z` 和主动预加载数量控制显示。
- 3.0 使用 NoteType 的 `ZNear/ZFar`，并按 `distance - currentDistance + posZ * zScale` 判定可见窗口。
- 影响：同一个音符可能在 Maker 更早出现、更晚消失、命中前仍存在或命中时已经回收；视觉上表现为轨道密度、提前量和白框贴合度不同。
- 处理优先级：P1。统一 NoteType near/far、命中零点和 culling 语义；预加载只优化实体创建，不改变可见窗口。

#### A5. 特效不保证全量一致
- Maker 是命令侧/服务端 `playTrackEffect()` 分派，文本/粒子/药水/轨道等事件由 Maker 自己解析 JSON。
- 3.0 是 `EffectManager`、持久 Effect 和 `GpTextDisplay` 的对象生命周期；`TEXT_DISPLAY_SYNC_TRACK` 会每更新帧同步轨道，`TEXT_DISPLAY_DESYNC_TRACK` 主动解除绑定。
- 影响：TEXT_DISPLAY/Hologram 的相对原点、初始属性、旋转/缩放矩阵、duration、插值、glow/background/shadow/opacity、多行 contents 和移除事件可能不一致；普通轨道同步特效也可能只在 Maker 触发瞬间而非持续更新。
- 处理优先级：P1。按 3.0 EffectType 建立事件能力矩阵，所有持续效果实现 start/update/end 三阶段；同步轨道效果必须在每个播放 tick 依据同一 Beat 更新。

#### A6. 音符材质/类型映射分叉
- 3.0 通过 NoteSkin 选择 Material；Maker 通过 `blockStateForType()` 选择 BlockDisplay 方块状态。
- 影响：视觉颜色、发光、LOOK/TAP/HOLD 形态和特殊音符表现可能不同；这不一定是坐标问题，而是渲染资源不一致。
- 处理优先级：P1。建立 `NoteVisualSpec` 映射表，按 3.0 的 NoteType 和默认 NoteSkin 明确材质、颜色、旋转、缩放、HOLD 首中尾规则；Maker 预览使用同一表。

### B. 可能存在但需用实际 JAR/黑盒确认的差异
- Reborn ZIP 与用户实际 3.0 发布版本是否完全同 commit/同配置。
- 3.0 音频播放的底层设备启动延迟、暂停恢复和 seek 行为；当前参考源码中主游戏逻辑以 elapsedMillis 为权威，但必须查实际音频播放器/客户端调用。
- `TrackPlayback.ease()` 与 3.0 `EasingUtils` 的全部编号是否逐项完全一致；当前看到 Maker 有 0~33 映射，但仍需逐编号输出数值对照，特别是常量/阶跃/弹跳 easing。
- 3.0 是否对某些谱面版本做了前置转换、旧字段兼容、单位缩放或 chart origin 修正。
- TextDisplay 的客户端插值是否由服务器端 entity metadata 发送节奏决定；仅靠源码静态阅读不能证明最终帧级视觉相同。

## 建议的深层解决方案

### 阶段 1：建立兼容性契约，不先改视觉细节
1. 定义 `RhythmcPlaybackContract`：
   - `Timing`: BPM 事件、offset、beat<->millis、播放速率、seek。
   - `Track`: speed 积分、轨道变换、easing、默认值、事件边界。
   - `Note`: 类型、局部坐标、命中 Beat、near/far、材质规格。
   - `Effect`: start/update/end、duration、相对原点、轨道绑定。
   - `Coordinate`: 判定线原点、Z 方向、Y 中心、旋转顺序、缩放顺序。
2. 将 Maker 内部所有播放对象从“各处自己算”改为消费该契约；不要让 UI 时间轴、正式播放、滚动播放各自维护独立 Beat。
3. 把 3.0 规则当作唯一参考实现；如果 Maker 需要场景单位换算，明确放在单一 `WorldScaleAdapter`，禁止散落倍率。

### 阶段 2：先修正音符/轨道主链路
1. 核准并移除或显式解释 `PLAYBACK_FLOW_MULTIPLIER=5.0`；通过同一谱面测量 3.0 `distance(beat)` 与 Maker 世界距离，建立自动比对表。
2. 用共享的速度积分和 easing 表替换 Maker `TrackPlayback` 独立实现；处理事件未开始、事件结束、零时长、重叠、负速度和浮点端点。
3. 统一 `NoteRenderTransform`，严格复刻 3.0 的 `computeRenderState()`：局部位置缩放、Z 方向、旋转顺序、轨道平移、最终世界位置。
4. 统一 NoteType 可见窗口与命中点；预加载池只能改变创建时机，不能改变几何状态。
5. 用 3.0 NoteSkin 建立 Maker BlockDisplay 对应资源；如果无法完全复刻材质，至少锁定颜色、大小、发光和姿态。

### 阶段 3：重建特效播放兼容层
1. 对所有导出事件建立能力矩阵：普通文字、TextDisplay 初始化、文字/背景/阴影/透明度/发光、线性变换、轨道同步/解绑、Hologram、粒子、药水、移除。
2. 每个持续事件维护 `EffectRuntimeState`，使用同一 Beat 在 update 阶段刷新；不能只在事件起点设置一次属性。
3. 统一 TextDisplay 原点：3.0 的 `screenCenterLoc`/相对位置与 Maker 的 `(TEXT_DISPLAY_CENTER_X=200.5, TEXT_DISPLAY_CENTER_Y=66.0, TEXT_DISPLAY_CENTER_Z=-1.0)` 必须通过可配置 `EffectSceneOrigin` 映射；不得把相对坐标误当世界绝对坐标。
4. 统一矩阵组合和客户端插值策略：`translate -> rotateXYZ -> scale`，明确角度单位、轴顺序、初始矩阵和插值 tick。
5. 事件清理必须覆盖自然到期、移除事件、停止播放、seek 后重建四种路径。

### 阶段 4：统一音频/seek/播放生命周期
1. 构建单一 `ChartPlaybackClock`，保存 `targetBeat`、`targetMillis`、`playing`、`rate`、`generation`。
2. 播放按钮、拖动时间轴、暂停/恢复、重新播放都只调用 clock 的 `seek/play/pause`；音符、轨道、特效、判定音和玩家/判定线位置从 clock 读取。
3. 音频建立可 seek 的 buffer/播放器；seek 时先暂停旧实例，再设置毫秒位置，重新建立时钟锚点，避免声音沿旧时间继续跑。
4. seek 后重置 note/effect cursor，并按目标 Beat 重建所有持续特效状态；不能只移动 UI 播放头。
5. 播放结束与关闭时释放音频、实体池、TextDisplay、状态效果和玩家绑定，恢复玩家原位置/朝向。

## 验收方案（交给编译合作方）

### 1. 数值级对照
准备一张同时含有：BPM 变化、offset、speed easing、轨道旋转/缩放/平移、分数位置小数、TAP/LOOK/HOLD、TextDisplay 同步轨道的最小谱面。
- 在 Beat `0, 1, 4, 8, 16, 32` 导出两边：current distance、轨道 pose、note world position/rotation/scale、effect state。
- 要求：相同 chart 单位下误差小于 `1e-5`；若存在明确世界缩放，仅允许在一个适配器中出现并记录比例。
- 检查 3.0 实际发布 JAR 与 Reborn ZIP 是否一致；不一致时以 JAR 黑盒结果为准。

### 2. 音频与时钟
- 用含 offset 和变 BPM 的 6 分钟谱面，从 Beat 0、Beat 128、Beat 512、末尾分别播放/seek。
- 比较音频播放位置、白框/判定线、音符命中音、轨道姿态、特效状态。
- 要求 seek 后三者都落在同一目标 Beat；连续播放 6 分钟不能出现可感知累积漂移。

### 3. 特效
- 覆盖 TEXT、HOLOGRAM、TEXT_DISPLAY_EFFECT、BACKGROUND_COLOR、SHADOW、OPACITY、GLOWING、LINEAR_TRANSFORMATION、SYNC_TRACK、DESYNC_TRACK、REMOVE。
- 检查相对原点、旋转顺序、缩放、颜色/透明度、duration、自然到期、显式移除、seek 重建和停止清理。

### 4. 视觉/实体
- 检查 TAP/LOOK/HOLD 的材质、颜色、大小、发光、出现/消失窗口和命中位置。
- 检查多轨道、轨道反向/负速度、非均匀 scale、旋转 90/180 度、分数坐标和跨 chunk 长距离移动。
- 检查 Maker 预览截图与实际 3.0 游戏截图，不以“帧率稳定”代替“状态一致”。
