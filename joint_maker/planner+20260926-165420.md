# Planner 分析记录：RhythMC 3.0 Beat 与 Maker Beat 计算差异

- 日期：2026-09-26
- 对象：用户提供的 3.0 难度文件；meta BPM=260、offset=0、1 条 Track、1257 个 notes。

## 3.0 文件的 Beat

- 3.0 直接在每个 note 对象保存 `beat`，例如 42、48、56.5、62.75、25.1666666666667、66.3333333333333。
- Beat 是谱面的逻辑节拍位置，不是由 `pos` 反推，也不是由歌曲毫秒时间四舍五入得到。
- `pos` 只描述音符在 Track/场景中的空间位置；同一 Beat 可以有多个不同 pos 音符。
- `meta.bpms` 保存 Beat→歌曲时间的映射参数；示例只有 beat 0、BPM 260，因此理论无变速区间为 `seconds = beat * 60 / 260`，offset 作为播放时间边界修正。
- Track 的 `startBeat/endBeat` 同样直接使用 Beat；示例速度事件覆盖 `0.0` 到 `571.419862`，不是按 Chunk 或方块位置计算。

## RhythMC-Reborn 运行时计算

- `TimingManager` 先按 BPM 事件 beat 排序，为每个 BPM 事件计算累计时间；`beatToMillis` 按所在 BPM 区间计算毫秒，`calcBeat` 做反向换算。
- 当前 Reborn 代码的 `beatToMillis` 返回 long，会在毫秒边界进行 Math.round；逻辑 Beat 本身仍保持 double。
- offset 在 TimingManager 的播放时间计算中作为毫秒边界加入/扣除，不能改变 note 的 beat。

## Maker 当前计算

- 3.0 导入：保留源 `note.beat`；使用 `ChartTiming.beatToSeconds(note.beat)` 生成 `note.time`；按 `note.z = -3 - note.beat * chart.divisionsPerChunk` 生成编辑空间 Z；X/Y 直接来自 3.0 `pos`，Y 加 66。
- Maker 的 `ChartTiming` 支持多 BPM、double Beat，并以秒作为连续值，通常比 Reborn 的 long 毫秒中间值保留更多精度；这是合理差异。
- Maker 手动在方块上放置音符时，用 `slot = -z - 3`、`beat = slot / divisionsPerChunk`；该 Beat 来自 Maker 自己的编辑网格，不是 3.0 文件直接计算方式。
- 当前手动放置代码仍使用 `note.time = note.beat * 60.0 / chart.bpm`，没有调用完整 `ChartTiming.beatToSeconds`，并且未显式加入 offset；遇到变 BPM 时会与 3.0/导入路径产生差异。这是需要后续修复的真实问题。
- Maker 修改每 Chunk 分数时会用 `note.z = -3 - beat * divisions` 重排空间位置；这只影响编辑器空间，不应修改 `note.beat`。

## 结论

- 3.0 Beat 与 Maker 导入后的 `note.beat` 在设计上应当完全相同；当前导入路径已经做到保留 Beat。
- 两者真正不同的是 Beat→time、Beat→空间 Z 和手动放置反算：3.0 不使用 Maker 的 divisionsPerChunk；Maker 为编辑显示新增该空间倍率。
- 3.0 `pos` 不能用来计算 beat；不能拿 pos.z 或 Chunk 位置替代 note.beat。
- 用户提供的文件中存在小数 Beat，使用默认每 Chunk 4 时自然会出现小数 Z/BlockDisplay，这是显示映射结果，不代表 Beat 被错误计算。
