# 进入已创建/导入谱面世界缓慢：性能诊断

## 任务边界与证据等级

本轮为 Planner 静态诊断；没有修改 Maker 源码、没有编译或运行测试。读取了实例 `logs/2026-10-24-2.log.gz` 和当前 Maker 源码。

- **运行日志事实**：2026-10-24 19:43:09 开始“Loading 121 persistent chunks”；进度在 72% 后长时间停留；19:43:40 报 `Time elapsed: 31543 ms`，19:43:41 玩家才完成登录。19:43:29 有服务器落后 2063ms/41 ticks 警告。
- **证据边界**：这段日志属于启动/进入“新的世界”的 Integrated Server，不是一次带有 `rhythmc_enter <chartId>` 命令记录的既有谱面维度切换；因此它证明世界初始化/玩家出生区块准备耗时严重，但不能单独证明该次 31.5 秒全部发生在 `rhythmc_enter` 路径。
- **源码定位到的确定缺陷**：服务端每 tick 对所有 Maker 编辑器世界无条件执行播放区域区块加载；加载缺失区块时调用 `setChunkForced(true)` 并同步 `getChunk()`。该逻辑与“播放会话是否存在”无关，而且没有在该播放区块加载路径对应的停止播放处释放 ticket。

## 主要根因（P0，高置信代码缺陷）

`RhythmcMaker.onInitialize()` 注册的 `ServerTickEvents.END_SERVER_TICK` 每 tick 执行：对 `server.getWorlds()` 中每个 `isEditorWorld(world)` 调用 `ensurePlaybackChunksLoaded(world)`（约 280 行）。后者逐个检查中心播放区域 9×9、最多 81 个区块；每遇未加载区块便 `world.setChunkForced(x,z,true)` 再同步 `world.getChunk(x,z)`（约 2344–2357 行）。

其影响：

1. **空闲也加载**：进入普通世界或闲置谱面维度时，只要它被纳入当前 server world 列表，就会尝试载入播放区域；不要求播放会话活动。
2. **每个维度扩散**：循环覆盖所有 Maker 编辑器世界，而不是仅当前玩家所在维度或正在播放的维度。已有多张谱面维度时，加载/区块 ticket 数量会按维度数扩大。
3. **同步阻塞主线程**：`getChunk()` 在服务端 tick 线程同步请求区块，磁盘读取、区块 NBT 解码、区块实体/实体加载或生成可直接造成 MSPT 暴涨和操作迟滞。
4. **强制 ticket 泄漏/持久化风险**：该 helper 只在 chunk 尚未加载时设 forced=true；播放停止处 `stopPlayback()` 清理播放实体和 session，但没有释放这 9×9 区块的强制加载。每 tick 再调用时区块已加载，直接 return，不会记录或回收这些 tickets。区块强制加载可能随存档持久化，解释为何后续进世界要准备大量 persistent chunks。
5. **启动证据吻合但不能单独归因**：日志中的 121 persistent chunks 与上述玩法有数量级关联（一次维度最多 81 个播放区块，加上 hub、谱面轨道/场景清理短期 ticket 等）；不过不同维度的持久 ticket 计数、其他模组与存档历史也可能贡献，当前不能将 121 全部算到 Maker。

另一个调用点是正式播放开始时 `startPlayback()` 调一次 `ensurePlaybackChunksLoaded(world)`，播放循环期间 `processPlaybackSessions()` 也对活跃 session world 调用。两者属于合理的播放需要；应保留按会话加载的必要能力，但移除/重构全局空闲维度加载路径。

## 次要成本（P1，进入已有谱面维度路径）

`enterChartDimension()`（约 588–646 行）在命令执行中同步做一组世界操作：

- `ChartStorage.find()` 读取并解析谱面元数据；`saveChart()` 在此处是缓存标脏，不是同步落盘。
- `ChartDimensionManager.getOrCreate()` 取已加载维度，或通过 ArcadeDimensions 加载已有 CustomLevel。
- `clearAllChartNoteDisplays(editor)` 遍历目标维度中全部 BlockDisplay 并删除 note-tag 实体，不限当前谱面 ID；大型/陈旧 display 数量会使进入命令延迟。
- `hasEditorTrack()` 读取区块状态；轨道不存在时 `restoreEditorTrackFoundation()` 同步写一批方块，`extendEditorArea()` 剩余部分按每 tick 8 列排队构建。
- `refreshNoteDisplays()` 只排队；之后每 tick 最多处理 64 个音符实体，并按块清扫遗留显示。
- 玩家实际跨维度传送还要等待 `DIMENSION_TRAVEL_READY` 与 `PENDING_EDITOR_ENTRIES` 的 tick 流程。

因此谱面音符数量主要影响进入后的异步显示恢复时长，不等同于进入命令本身必然同步处理所有音符。若现象是“世界已出现但音符/轨道逐渐补齐”，这部分是独立阶段。

## 其他启动期开销线索

`SERVER_STARTING` 会调用 `installHubMap()`；若 marker 缺失会拷贝四个 region 文件并移动到存档。该操作发生在启动阶段但不是每次进入谱面世界；只在首次安装/marker 丢失时运行。代码还有 `verifyStaticEditorPool()` -> `ChartDimensionManager.preloadCharts()` 的实现，但本轮未找到其调用点，不应把批量预加载认定为当前确定根因。

## 推荐修复顺序（供实现方）

### P0：先截断空闲区块加载

- 删除服务端每 tick 对所有 editor worlds 的 `ensurePlaybackChunksLoaded()` 调用。
- 播放区块加载只由活动 `PlaybackSession`/确实需要场景预览的活动会话触发，不因世界存在而触发。
- 加载前建立按维度、按用途的 ticket ownership；停止播放、关闭预览、玩家离开维度、会话异常结束时成对释放。不要仅以 `isChunkLoaded()` 当作 ticket 状态。
- 不要在每 tick 同步 `getChunk()` 81 次；首次准备按有限预算分批完成，并明确未准备完成时播放/相机的行为。这里是加载实现建议，不改变播放时钟、音符/判定逻辑。
- 启动时清理历史残留的 Maker 播放区块 forced ticket（需辨明 Maker 自有 ticket 与用户/其他模组 ticket，不能盲目取消其他用途的强制加载）。

### P1：减少谱面切换同步扫描

- `clearAllChartNoteDisplays()` 改为按目标谱面 tag 清理；如确有跨谱残留清理，按 chunk 分批/按 generation 清理，避免整维度全实体扫描。
- 对轨道修复和音符 display refresh 保持有界 tick budget；进入命令只做必需的状态切换，工作进度异步反馈。
- 缓存已解析 ChartManifest/目标维度；避免反复 manifest IO/JSON parse。

## 验证计划与缺失反馈环

当前没有运行中的游戏控制权或 Spark profile，因此无法按 diagnosing-bugs skill 建立“已执行且可重复”的红灯反馈环，也无法从静态源码确认具体某次已有谱面进入时的 wall-clock 分解。建议实现前后用同一存档做对照：

1. 登录普通 hub、不进入谱面；测启动/登录耗时及 `persistent chunks` 数。
2. 进入一张小谱面与 6 分钟/数千 note 谱面；分别记录命令至传送、传送至可编辑、传送至音符显示完成时间。
3. Spark 对 integrated server 做 60 秒 profile，重点看 `ensurePlaybackChunksLoaded`、`ServerChunkManager.getChunk`、`ChunkMap/AnvilChunkStorage`、`clearAllChartNoteDisplays` 与 `processEditorNoteRefreshTasks`。
4. 进入后退出播放/返回 hub，再重启；检查 Maker 区块强制列表是否随闲置维度/谱面数增长。
5. 修复后同存档确认普通登录不加载所有谱面维度播放区块；只有启动播放或场景预览时加载必要区域，结束后释放；MSPT 与登录阶段时间显著下降，且滚动/正式播放功能不变。
