# 滚动播放导致制谱器操作响应延迟诊断

- 日期：2026-10-02
- 用户补充：滚动播放期间和滚动播放结束后均出现操作响应延迟；滚动播放之前无问题。表现不是 FPS 下降，而是类似多人服务器延迟。
- 当前基线：`maker+20261002-001206.md`、`maker+20261001-232605.md`、`maker+20261001-231916.md`。
- Planner 边界：仅分析和规划，不修改源码、不编译、不测试、不部署。
- 证据限制：当前没有最新 `latest.log`、Tick 耗时采样、谱面音符数量或结束后延迟持续时间，因此将源码确认事实与高优先级推断分开说明。

## 结论

滚动播放并不是“客户端只移动一个白框”。当前实现仍会向服务端发送 `rhythmc_play ... scroll ...`，创建完整的 `PlaybackSession`。由于单人/集成服务器的服务端与客户端运行在同一 Minecraft 进程中，滚动播放期间的服务端 Tick 工作会直接竞争制谱器的输入、世界更新、命令处理和 UI 响应时间。

因此最可能的根因是：**滚动模式关闭了正式显示实体分支，但没有关闭服务端播放会话和音符处理链路；它仍在服务端主线程持续扫描谱面并处理到时音符。** 这能解释播放前无延迟、播放中出现类似网络延迟的操作滞后。播放结束后仍延迟，则需要进一步检查会话停止命令、结束清理、自动保存和已经积累的 Tick/网络任务是否在结束阶段集中执行。

## 已确认的代码路径

### 滚动播放仍启动服务端会话

客户端 `beginPlayback()` 设置 `playbackMode = "scroll"` 后，仍构造并发送 `rhythmc_play <chunk> scroll <rate>`。服务端 `togglePlayback(...)` 对 `scroll` 只把 `formal` 设为 false，仍然创建 `PlaybackSession` 并放入 `PLAYBACK_SESSIONS`。

服务端每个 `END_SERVER_TICK` 都依次运行多组任务，最后运行 `processPlaybackSessions(server)`。因此滚动播放期间不会因为“不创建正式实体”而退出播放主循环。

### 滚动分支仍逐条扫描到时音符

在 `processPlaybackSessions(...)` 中：

- 正式模式执行特效处理、活动 Display 遍历、预载和实体位置更新。
- 滚动模式虽然跳过正式 Display 分支，但进入 `else`：
  - 持续检查 `nextNoteIndex`。
  - 对所有 `noteTime <= songTime` 的音符递增索引。
  - 对每个到时音符调用 `playHitSound(...)`。

这意味着滚动播放仍会对整张谱面的音符做时间推进和音效处理。若单个 Tick 因卡顿跨过很长时间或谱面在同一时间有大量音符，while 循环可能在一个 Server Tick 内批量处理大量音符和声音包。

### PlaybackSession 构造也在主线程制造启动尖峰

构造会话时会：

- 准备 `ChartTiming`。
- 准备 `PlaybackDistance` 和每条轨道的 `TrackPlayback`。
- 复制并排序 notes/effects。
- 为所有音符建立 `notesById` 和 `noteTimes` 映射。
- 计算结束时间并跳过起始 Beat 以前的音符。

大谱面开始滚动播放时，这些操作发生在服务端命令处理/主线程路径，可能造成启动瞬间的输入响应延迟；这与“播放前正常、点击播放后开始卡”的时间关系一致。

### 客户端也有持续 Tick 工作

客户端播放期间每个 `END_CLIENT_TICK` 会继续处理：

- 场景操作状态和状态提示。
- 编辑器 sidebar 快照。
- 音频进程状态、启动/结束检测。
- 播放命令发送和失败清理。

滚动白框本身在 `WorldRenderEvents.AFTER_ENTITIES` 中绘制，通常不应单独造成明显输入延迟，但它使用 `resolveActiveChart()`、播放时间和坐标映射；仍应测量而不是凭 FPS 排除。

## 为什么“不是掉帧，而是操作响应慢”

Minecraft 的 FPS 主要反映渲染线程/帧提交，不能代表以下路径没有阻塞：

- 客户端 Tick 回调。
- 集成服务器 Tick。
- 命令发送与服务端处理。
- 世界/实体/声音包更新。
- 输入事件排队到下一次 Tick 的延迟。
- GC 或文件 I/O 停顿。

在单人集成服中，服务端 Tick 和客户端共享 Java 进程资源；即使渲染画面仍能保持较稳定帧率，主线程或集成服务端处理超时也会让鼠标、键盘、点击和命令像网络延迟一样滞后。

## 播放结束后仍延迟的可能路径

### 高优先级：客户端停止命令晚于音频结束

客户端检测到 ffplay 结束后，才调用 `finishPlayback(...)` 并发送 `rhythmc_stop_playback`。在停止命令到达并由服务端处理前，`PLAYBACK_SESSIONS` 仍可能存在；服务端会继续执行播放会话直到收到命令或达到 `endSeconds`。

这会造成结束后短时间的残余延迟，但通常应是有限时长。需要记录音频退出、客户端发送停止命令、服务端移除 session 三个时间点。

### 中高优先级：结束时清理扫描

`stopPlayback(...)` 会：

- 从 `PLAYBACK_SESSIONS` 移除 session。
- 清理 glow team。
- 删除 session displays 和 displayPool。
- 再调用 `world.getEntitiesByType(BLOCK_DISPLAY, predicate)` 扫描世界寻找带玩家标签的残留实体。

滚动模式通常没有 session displays，但停止路径仍可能执行清理逻辑；若世界中存在大量相关 Display 或历史残留，结束清理可能造成主线程尖峰。需要记录扫描数量和耗时，不能直接假定这是主要根因。

### 中优先级：自动保存与其他 ServerTick 任务

服务端每 Tick 在播放会话前后还会处理场景导入、编辑区任务、轨道重建、场景捕获、音符刷新、区块清理、实体清扫、sidebar 刷新和周期性自动保存。播放结束时如果恰好触发自动保存或编辑任务完成，用户会感知为“播放结束后仍卡”。需要将这些任务与播放处理分别计时。

### 需要排除：残留 PlaybackSession

按当前 `songTime >= session.endSeconds` 逻辑，session 理论上会被移除；如果结束后长时间仍延迟，必须检查是否存在异常路径、停止命令未到达、session 被重新创建或其他任务残留。不能仅凭现象认定是 session 泄漏。

## 最优先的修复方向

### 方案 1：滚动播放不创建服务端完整 PlaybackSession

如果滚动播放的产品定义只是客户端白框/滚动位置预览，不需要服务端播放音符实体、服务端命中音效或特效触发，那么应将滚动模式改为客户端本地播放状态：

- 客户端启动音频并维护统一的播放时钟。
- 客户端只渲染白框和必要的本地预览。
- 不发送会创建 `PlaybackSession` 的 `rhythmc_play ... scroll` 命令。
- 不进入服务端 `processPlaybackSessions(...)`。
- 音频结束时只清理客户端状态，不发送多余的服务端停止命令；若此前存在旧 session，先提供一次性兼容停止。

这是最可能同时解决“播放中卡顿”和“滚动模式额外服务端负担”的根治方案，但必须先确认滚动播放是否确实需要服务端音效/特效/世界状态。

### 方案 2：滚动播放保留服务端会话但关闭无关工作

如果滚动播放必须触发服务端音效或特效，则应为 `scroll` 建立轻量 session：

- 不复制/排序不需要的 notes/effects。
- 不执行正式实体分支。
- 明确只保留确实需要的音效/特效事件。
- 对到时事件增加每 Tick 预算和可观测积压计数，防止一帧处理无限历史音符。
- 缓存预计算时间数组，避免每次创建播放会话都重做全谱面准备。
- 播放结束后立即移除轻量 session，避免继续走完整任务链。

### 方案 3：清理和保存路径降峰

- 停止时只清理当前 session 记录的实体；避免无条件全世界 `getEntitiesByType` 扫描，或将孤儿清理改成分批后台任务。
- 将大文件保存和谱面序列化从关键 Tick 路径移开；涉及 Minecraft world/entity 的提交仍回主线程。
- 为自动保存、场景任务、编辑轨道重建和播放处理分别设预算，避免同一 Tick 叠加。

## 必须先采集的证据

1. 滚动播放模式下 `PLAYBACK_SESSIONS` 数量、session 起止时间和每 Tick 是否持续存在。
2. `processPlaybackSessions` 总耗时，以及其中滚动分支 while 音符循环耗时/处理数量。
3. `PlaybackSession` 构造耗时、notes/effects 数量、TrackPlayback 准备耗时。
4. 客户端 Tick 总耗时、`updateEditorSidebarSnapshot`、音频状态检查和白框坐标计算耗时。
5. 播放结束时 stop 命令发送、服务端 session 移除、Display 扫描数量/耗时、自动保存耗时。
6. 播放前/播放中/播放后 client tick、server tick 的 p50/p95/max 和输入响应时间。
7. 在同一谱面分别运行：不播放、滚动播放但不发服务端会话、当前滚动播放三组对照。

## 验收标准

### 播放期间

- 滚动播放不再执行与产品需求无关的正式音符实体、发光队伍和服务端全谱面处理。
- 操作响应延迟与未播放状态接近；不能只报告 FPS。
- 大谱面开始播放时不存在明显同步构造尖峰。
- 客户端白框继续使用已统一的播放坐标映射和时间锚点。

### 播放结束后

- 音频结束、客户端状态清理、服务端 session 移除和 UI 响应恢复顺序明确。
- 不存在残留 session、音频进程、停止命令积压、显示实体或重复自动保存任务。
- 结束清理不产生明显长 Tick。

### 数据与功能

- 若滚动播放仍需音效/特效，轻量 session 必须保留这些功能；若不需要，则完全客户端化。
- 正式播放仍保持独立的实体、命中和服务端逻辑，不因滚动模式修复而改变正式播放行为。

## 交给实现方的任务清单

1. 明确滚动播放是否需要服务端音符命中音效、特效和世界状态；这是选择客户端化还是轻量 session 的关键决策。
2. 给 `processPlaybackSessions`、滚动 while 循环、session 构造、停止清理和自动保存加低侵入耗时/计数日志。
3. 做“当前滚动模式 vs 不创建服务端 session”的对照测试。
4. 若滚动只需白框和音频，移除滚动模式的 `rhythmc_play` 服务端会话路径。
5. 若必须保留服务端事件，新增轻量 scroll session，限制每 Tick 工作量并缓存预计算结果。
6. 修复播放结束后的停止协议和清理路径，确保状态在音频结束时立即一致清除。
7. 编译、运行、采样和部署由执行方完成；Planner 不执行工程修改。

## 本轮结论

滚动播放期间卡顿的首要嫌疑不是白框绘制，而是滚动模式仍启动了完整服务端播放会话；在集成服务器中，这些服务端 Tick 工作会直接拖慢制谱器的输入和操作响应。播放结束后仍延迟，则优先检查停止命令到达、session 移除、全世界 Display 清理、自动保存和其他 ServerTick 任务。最优先的架构选择是：若滚动播放只承担白框预览，就改为客户端本地播放；若必须触发服务端事件，则实现专门的轻量滚动会话，而不是复用正式播放会话。
