# Maker 本地特效预览性能方案（对照 Reborn TextDisplay）

日期：2026-10-24

## 结论

Maker 并非没有使用 Reborn 的思路：当前已经有 TextDisplay 活动映射/对象池、轨道姿态缓存比较（epsilon 差分）、对象重置复用、播放会话生命周期清理。下一步不应重复造一套池，而应先解决 seek 命令风暴与时间轴跳转时的状态重建；之后消除每 tick 的临时分配，并补齐对象池的跨 seek 复用和容量治理。

## 当前实现核对

### 已具备

- `PlaybackSession` 有 `textDisplays` 与 `textDisplayPool`，显示通过 ID acquire/release；release 隐藏实体、清空文本并回池。
- `updateTextDisplays()` 按活动显示逐个检查有效期；对轨道绑定对象根据 beat 查询轨道 pose，并与上次 pose 以 `1e-5` 容差比较，未变化时不再写入实体变换。
- 每 tick 的轨道 pose 在本 tick 内按 track ID 复用，避免同轨道每个 TextDisplay 重复求值。
- `TEXT_DISPLAY_SYNC_TRACK`、`DESYNC_TRACK`、`REMOVE` 与有时限显示均有对应状态和清理路径。

### 主要剩余开销

1. 时间轴拖动期间 `EffectEditorImGuiView` 每次鼠标采样都调用 `seekTimelineBeat()`；beat 变化就调用 `seekAction`。客户端随即发送 `rhythmc_effect_preview_seek`。播放中，`seekEffectEditorPreview()` 还会停止并重新启动本地音频进程。因此高刷新率鼠标拖动会产生连续服务器命令、音频重启和服务端 seek 工作。
2. 服务端 seek 路径调用 `ScrollJudgementSession.seekToBeat()`，其会清理效果会话；游玩会话的恢复路径会按目标时间重建持续效果。`PlaybackSession.initializeTextDisplays()` 从效果列表开头扫描到目标时间并逐个回放文本相关事件，复杂长谱/频繁拖动时可能重复处理大量历史事件。
3. `updateTextDisplays()` 每次更新都创建 track→Pose 的 HashMap；同步的每个 TextDisplay 创建 `nextPose` 数组，差分通过后又创建位置/旋转/缩放数组并替换缓存数组。即使多数对象无变化，仍有临时分配；大量同步显示时会增加 GC 压力。
4. 现有 `textDisplayPool` 是会话局部池；清理会话时 `clearTextDisplays()` 会连活动对象与池内对象一并 remove。反复 seek/重建若触发该清理，池的复用收益局限于单次会话。
5. 池没有可见的硬容量上限/高水位回收策略；异常谱面或超高同时活动数量可能让池和服务器实体数量偏大。

## 推荐实施顺序

### P0：合并 seek 请求，避免命令/音频重启风暴

- UI 播放头仍按鼠标每帧即时移动，保持手感；服务器和音频更新改为一个“最新目标 Beat”槽位，由单个调度器合并连续输入，不排队发送每一帧的旧目标。
- 拖动期间按固定节流频率提交同步跳转事务（建议先从 10–20 次/秒设计并实测）；每个事务取同一个最新 Beat，由同一 ChartTiming 将它映射为音频位置、服务器播放进度和玩家/判定线 Z。松开鼠标时立即 flush 最后一个目标，确保最终状态精确一致。
- 音频端不要每次鼠标 move 都 stop/start 外部播放器。优先采用可 seek 的长生命周期音频流/buffer；若短期仍沿用当前进程播放方式，至少拖动开始只停一次，拖动中节流重定位，结束时提交并按原播放状态恢复。事务需带单调递增序号/会话 token，丢弃过期命令响应，防止旧 Beat 覆盖新 Beat。
- UI 选择单个特效、键盘逐格移动也复用同一合并器；连续选择/拖动完成后执行一次最终对齐。
- 不建议将服务端 seek 只延迟到鼠标松开：这会破坏现有“拖动即同步 seek 音频/服务端/玩家位置”的交互约定。应限频并合并，而不是拆成仅 UI 预览。

### P1：把 seek 状态重建从“扫描全历史”改成索引/检查点

- 谱面装载或保存后，离线构建排序好的 TextDisplay 事件时间索引；运行时不再每次线性扫描全部事件。
- 每隔固定时间/小节或固定事件数生成文本显示状态检查点：ID→文本、位置/旋转/缩放、样式、轨道绑定、过期时刻等。
- seek 时二分查找最近检查点，从该检查点恢复状态，再仅回放 checkpoint→target 区间内的事件；音符音频与 ChartTiming 的基准Beat仍使用同一时间映射，不改变效果逻辑顺序。
- 插入、删除或修改特效后只重建受影响区间之后的检查点；可先采用全量异步重建的较小实现，再根据谱面规模做增量化。
- 检查点保存纯数据，不保存 Minecraft Entity 对象；实体映射/池仍由服务端播放会话拥有。

### P2：同步轨道的热循环零/低分配

- 将 track pose cache 变为会话复用的 scratch map 或按 track 数量索引的数组；每 tick 覆盖，而不是 new HashMap。
- `textDisplayLastPoses` 中的 9 个 double 缓冲数组原地更新，避免每个 display 每 tick new 数组；变换分量确定变化后只构造一次最终变换对象/参数。
- 将 pose 差分封装为无分配数值比较；仅改变小于可接受视觉阈值时才跳过写回。阈值需测试，不能为了降低开销引入肉眼可见抖动或轨道偏差。
- 静态文本不参加持续 pose 更新循环；维护独立的 `trackedTextDisplayIds` 集合，循环只扫真正绑定轨道的活动实体。过期检查也可按最早过期时间队列处理，避免对所有静态显示每 tick 查询多个 Map。

### P3：扩大池复用并控制峰值

- 将池从可销毁的瞬时播放对象调整为编辑器预览会话生命周期拥有：seek 时隐藏并 reset 活动实体，清空 ID/轨道绑定，将对象返回池；编辑器关闭/切歌/世界卸载时才真正 remove。
- 谱面预扫描 TextDisplay 创建/移除事件，计算同时活动数量峰值，预热峰值附近对象；预热和新建仍分 tick 限额，不在编辑器打开或 seek 的单一 tick 集中 spawn。
- 池设置最大保留容量和低水位，超过容量的空闲对象批量销毁；对活动数/池数/每 tick spawn-remove 做诊断计数，避免“预热”反而造成过量实体。
- 重置必须恢复所有复用属性（文本、透明度、背景、阴影、发光、尺寸、插值、变换、不可见状态），避免上一个效果的样式污染下一个 ID。

### P4（后续选项）：本地客户端轻量预览

- 如果服务端实体和实体跟踪仍是主要瓶颈，可单独做 client-only TextDisplay 几何预览：本地保存纯数据状态，由渲染器批量绘制，不创建服务端实体、不发实体元数据包。
- 该方案应只用于编辑器快速预览；保留 Reborn 兼容的实体回放/最终验证模式。要严格对齐 Minecraft TextDisplay 字体、背景、发光、矩阵顺序和裁剪范围，因此属于较大渲染改造，不应作为第一阶段替换。

## 推荐的代码责任边界

- `EffectEditorImGuiView`：只更新 UI playhead、收集拖动目标和鼠标释放事件；不直接造成每帧外部音频重启。
- `RhythmcMakerClient`：持有 seek 合并器、提交节流事务和音频同步；统一使用同一个目标 Beat/ChartTiming。
- 服务端 `ScrollJudgementSession`/`PlaybackSession`：接收最新序号的 seek，更新判定/世界位置并恢复该 Beat 的效果快照；不重复处理已过时请求。
- 新增纯数据 `TextDisplayTimeline/Checkpoint`：管理排序、快照和区间恢复，不直接操作 Minecraft 世界。
- TextDisplay Entity Pool：只管理 create/reset/release/destroy 和容量策略；播放事件/轨道时间逻辑不放入池管理器。

## 验收建议

- 6 分钟及更长谱面连续拖动时间轴 5–10 秒：客户端发送 seek 数量应受节流上限约束，不能随 FPS/鼠标采样线性增长；松手后保证最后一个 Beat 已提交。
- 每个提交事务记录目标 Beat、ChartTiming 得到的音频秒数、服务端当前 Beat、判定线 Z；三者误差在项目定义容差内。
- 同一目标 Beat 在“从头连续播放”与“直接 seek 到目标”两种方式下，TextDisplay 的 ID 集合、文本/样式/变换/过期状态一致。
- 对包含同步轨道的谱面测量每 tick pose 求值数、变换 setter 次数、临时分配量和 MSPT；静态文本不应随活动同步数量增加更新成本。
- 重复播放、seek、暂停、关闭编辑器、切世界后统计活动/池内 TextDisplay 数量；关闭或切世界后实体必须归零，无泄漏、重复实体或样式串扰。
- 测试高峰值谱面池上限与分批创建/销毁预算，确保单 tick 没有大批量 spawn/remove。

此方案依据 Maker 当前源码和此前已读取的 Reborn 源码快照做静态分析；没有运行 Spark/Profiler，也没有修改源码、编译或运行基准测试。实际收益排序应先用本地集成服务器 Spark 采样验证：命令/seek 负载、TextDisplay实体更新、GC、音频进程启动成本分别统计，避免把客户端画面 FPS 与服务端响应延迟混成单一指标。
