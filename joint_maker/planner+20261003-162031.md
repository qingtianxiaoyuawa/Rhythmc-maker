# RhythMC Maker 特效编辑器双虚拟视角规划

- 日期：2026-10-03 16:20:31（Asia/Shanghai）
- 身份：Planner；本轮不修改源码、不编译、不测试、不部署。
- 当前工程基线：`1.5.28`。

## 需求理解

特效编辑器需要两个虚拟视角，用于同时满足：

1. 编辑者观察和操作场景、音符、特效位置。
2. 预览最终播放时观众看到的镜头效果。

两个视角不能改变现有正式播放、判定音、时间轴、音符坐标和特效数据逻辑。

## 推荐架构

### 虚拟相机 A：编辑视角（Editor Camera）

用途：编辑器工作区中的自由观察和定位。

建议能力：

- 自由移动、旋转、缩放和环绕选中目标。
- 聚焦当前选中特效、音符、场景区域或时间轴游标。
- 显示网格、坐标轴、选中框、相机位置和朝向辅助线。
- 不参与最终播放，不写入正式特效事件。
- 编辑视角状态只保存在编辑器会话或编辑器偏好中，不混入谱面播放数据。

### 虚拟相机 B：预览视角（Preview/Output Camera）

用途：模拟最终播放时的镜头结果。

建议能力：

- 位置、旋转、视场角、裁剪距离和跟随目标可被特效轨道驱动。
- 时间轴移动时，根据当前 Beat/秒数采样相机关键帧。
- 播放预览时只改变 B 的状态，不改变 Minecraft 玩家位置。
- 可保存为谱面中的相机轨道，例如 `cameraTracks` 或独立的 camera event 数据。
- 没有相机关键帧时使用固定默认相机，保证旧谱面行为不变。

## 关键实现原则

### 不要创建两个真实玩家或两个旁观者实体

Minecraft 客户端同时只有一个实际主相机。创建两个玩家、切换旁观者实体或频繁修改玩家位置会带来：

- 网络同步和服务端状态污染。
- 玩家输入、碰撞、区块加载、视角切换异常。
- 正式播放逻辑与编辑器预览相互干扰。
- 退出编辑器后位置、游戏模式和状态恢复风险。

两个视角应是客户端渲染层中的纯数据对象，而不是世界实体。

### 第一阶段只实现“两个相机状态 + 单视角切换”

优先实现：

- A/B 相机均可独立编辑。
- `Tab` 或按钮切换当前预览相机。
- 时间轴拖动时只更新 B 的预览采样；A 保持编辑者观察位置。
- 这是最稳定、改动最小的版本，便于先验证相机轨道数据和特效采样逻辑。

### 第二阶段再实现“双视口同时显示”

如果确实需要同时看两个视角，再增加离屏渲染：

- 使用两个独立 framebuffer：`editorPreviewTarget` 和 `outputPreviewTarget`。
- 每个 framebuffer 使用各自的相机矩阵渲染同一场景。
- UI 中左侧显示 A，右侧显示 B，或主预览 + 小窗预览。
- 只在特效编辑器打开时启用；关闭界面立即释放 framebuffer。
- 不修改游戏主世界的真实相机和玩家状态。

双视口不是第一步就实现的功能，因为它会引入 framebuffer 生命周期、深度缓冲、实体渲染、透明层、后处理、窗口缩放和性能问题。

## 相机数据模型建议

建议将相机数据与现有 `effects` 分离，避免继续把所有数据塞进任意 `JsonObject`：

- `CameraTrack`
  - `id`
  - `name`
  - `enabled`
  - `defaultTransform`
  - `keyframes`
- `CameraKeyframe`
  - `beat` 或使用现有统一时间字段
  - `position`: x/y/z
  - `rotation`: yaw/pitch/roll
  - `fov`
  - `nearClip`
  - `farClip`
  - `easing`
  - `targetMode`
  - `targetId` 或目标坐标

建议初始只开放一个输出相机轨道 B；编辑相机 A 不写入谱面。未来若需要多个镜头，再扩展为多个 `CameraTrack`，但仍保留一个当前输出轨道。

## 相机采样与播放一致性

- 相机采样统一使用现有时间轴的 Beat/秒转换，不重新计算音符时间。
- 时间轴拖动、暂停、播放和循环预览共用同一个 preview clock。
- 相机插值只影响 B 的位置、旋转、FOV 等视觉参数，不改变音符生成、判定音和正式播放速度。
- 插值建议支持线性、平滑、阶梯三种基础模式；后续再扩展贝塞尔曲线。
- 播放结束时只清理预览相机覆盖，不清理玩家原始相机状态之外的游戏状态。
- 如果相机数据损坏，回退到默认固定相机，不影响谱面播放。

## 编辑器交互建议

### 视角切换

- 顶部显示 `编辑视角 A` / `输出预览 B`。
- 快捷键 `Tab`：切换当前查看视角。
- `锁定编辑视角`：防止时间轴播放时 A 被意外改变。
- `录制当前视角`：将 B 当前变换写入当前 Beat 的关键帧。
- `复制 A 到 B`：仅复制变换参数，不复制相机轨道或特效事件。

### 预览布局

第一阶段：

- 中央区域显示一个预览窗口。
- 左上角显示当前视角标记和相机状态。
- 右侧检查器编辑位置、旋转、FOV、跟随目标和插值。
- 底部时间轴只负责特效编辑和相机关键帧定位。

第二阶段：

- 主窗口显示 B 的最终预览。
- 右上角以小窗显示 A 的编辑观察视角。
- 小窗可切换为 B，便于性能较低时关闭双渲染。

## 渲染实现边界

### 推荐优先级

1. 复用当前世界和已有音符/场景实体渲染，只替换相机矩阵。
2. 先做单 framebuffer 单视角切换。
3. 再做双 framebuffer 双视口。
4. 最后才考虑后处理、景深、运动模糊等高成本效果。

### 不建议

- 用真实玩家传送来模拟相机。
- 用旁观者模式实体作为第二视角。
- 每帧创建和删除相机实体。
- 在服务端保存编辑器相机位置。
- 将编辑相机状态混入正式播放速度或音符位置计算。

## 性能与 Spark 验证

双视角会增加客户端渲染负担，不应只看服务端 Spark。验证应分两类：

- Spark：确认特效采样、服务端事件和世界更新没有因为预览相机增加额外 Tick 阻塞。
- 客户端性能：使用客户端帧时间、F3+L 或其他客户端 profiler，分别比较单视角、双视角、播放中双视角的 GPU/CPU 帧时间。

必须重点观察：

- 双 framebuffer 是否导致渲染线程峰值。
- 半透明粒子、BlockDisplay、场景方块是否被重复遍历。
- 时间轴拖动是否触发整场景重建。
- 相机更新是否错误触发服务端同步或谱面保存。

建议增加可关闭的双视口选项，并在低性能设备上默认使用单视角切换。

## 实施阶段

1. 抽象 `VirtualCameraState`，定义 A/B 两个纯客户端相机状态。
2. 实现 B 的时间轴关键帧数据和采样器；A 只保存编辑器会话状态。
3. 将当前特效编辑器预览从占位文本替换为单视角真实场景渲染。
4. 实现 A/B 单视角切换和相机关键帧录制。
5. 做播放、暂停、拖动、循环、保存和退出恢复验证。
6. 若单视角稳定且确有需求，再实现两个 framebuffer 的双视口。
7. 增加性能开关和客户端帧时间验收。

## 验收标准

- A、B 两个视角可独立移动、旋转和保存/恢复各自状态。
- A 不写入谱面；B 的关键帧可随时间轴编辑并正确插值。
- 时间轴播放只驱动 B 的预览相机，不改变正式播放逻辑。
- 关闭特效编辑器后，玩家位置、视角、游戏模式、音频和播放状态正确恢复。
- 旧谱面没有相机数据时仍使用默认预览相机且不报错。
- 相机数据损坏时回退默认视角，不导致客户端崩溃。
- 双视口开启时不会触发完整谱面重新解析、场景重复重建或服务端保存。
- 单视角模式下帧时间接近现有预览；双视角模式提供明确的性能开关。
