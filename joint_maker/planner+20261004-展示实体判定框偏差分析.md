# Text Display 展示实体判定框未贴合场景判定框的原因分析

- 日期：2026-10-04（Asia/Singapore）
- 身份：Planner；本轮只读取截图和源码并写入规划记录，不修改工程源码、不编译、不测试、不部署。
- 截图：`F:\b晴天小雨awa\程序\我的世界PCL\.minecraft\versions\Rhythmc 3.0\screenshots\2026-10-04_15.42.54.png`
- 最新制作基线：`maker+20261004-124500.md`，版本 `1.5.39`。

## 结论

紫色线框没有完全贴合青色判定框，主要不是单一坐标错误，而是以下三类定义混用：

1. 紫色线框显示的是 Text Display 实体的实体包围/显示边界，不是文字可视区域，也不是场景青色结构的几何边界。
2. 当前代码把 `displayWidth` 和 `displayHeight` 都粗略设置为 `2 * max(abs(scale))`，默认 scale 为 `(1,1,1)` 时得到约 `2×2` 的包围尺寸；它没有按青色结构的实际宽度和高度计算。
3. 当前文字实体基准位置仍是 `(200.5, 66.0, -1.0)`，而此前用户给出的判定框中心是 `(200.5, 67.0, -1.0)`，存在 1 格 Y 偏移。截图中紫框相对结构偏低/偏下的现象与该偏移相符，但仅凭透视截图不能把全部视觉差异都归因于这一项。

## 源码证据

### 1. 实体位置和文字变换原点

`RhythmcMaker.java` 的 `setTextDisplayPose()`：

```text
实体位置 = (TEXT_DISPLAY_CENTER_X, TEXT_DISPLAY_CENTER_Y, TEXT_DISPLAY_CENTER_Z) + effect.position
变换 translation = 0
变换 scale = effect.scale
```

当前常量为：

```text
TEXT_DISPLAY_CENTER_X = 200.5
TEXT_DISPLAY_CENTER_Y = 66.0
TEXT_DISPLAY_CENTER_Z = -1.0
```

因此事件默认位置 `(0, 1.5, 0)` 时，实际 Text Display 实体位置还会变成约 `(200.5, 67.5, -1.0)`；如果截图中的显示实体来自普通 `TEXT_DISPLAY` 事件，而不是仅来自初始化实体，那么不能只看基准常量，还必须检查事件 JSON 的 `position.y`。

### 2. 紫色边界尺寸不是文本尺寸

当前 `setTextDisplayTransform()`：

```text
bounds = clamp(max(abs(scale.x), abs(scale.y), abs(scale.z)) * 2.0)
display.setDisplayWidth(bounds)
display.setDisplayHeight(bounds)
```

这会让显示实体的边界成为一个由最大缩放分量决定的正方形。它没有使用：

- 文本实际像素宽度；
- `lineWidth`；
- 行数和字体高度；
- 目标判定框的世界宽度/高度；
- X/Y/Z 分别对应的实际包围尺寸。

而 `lineWidth` 目前只由 `display.setLineWidth(...)` 设置，不会反向把实体边界自动调整成青色结构尺寸。

### 3. 场景结构有自己的整数方块范围

播放区结构由 `buildPlaybackArea()` 用方块坐标生成：

- 底部高度约为 `Y=65`；
- 内部侧壁范围使用 `±wallHalfWidth`；
- 上部玻璃结构使用 `Y=68/69`；
- 前后结构使用 `Z=2` 和 `Z=-2`。

这套结构是方块面/方块空间边界，而 Text Display 的 display width/height 是实体边界，两者不是同一种几何定义。即使中心点相同，如果尺寸定义没有按结构内边界换算，也不会重合。

## 对截图的具体解释

- 紫色框整体落在青色结构内部，并且比青色开口小：说明当前 `displayWidth/displayHeight` 形成的实体边界小于场景结构范围。
- 灰色文字/图像只占紫框的一小部分：说明紫框不是文字可视像素框，而是实体的粗略显示/包围边界；文字渲染还受 Text Display 内部布局、缩放、对齐和文本内容影响。
- 紫框与青色结构的垂直位置不一致：优先检查 `TEXT_DISPLAY_CENTER_Y=66`、事件 `position.y`、以及方块结构按整数坐标生成后几何中心落在方块边界还是方块中心的问题。
- 截图存在透视投影，因此远近方向的边线不能直接用屏幕像素长度判断世界尺寸；应使用世界坐标或调试数值验证。

## 推荐修复方向

### 第一阶段：先统一坐标语义

实现方需要明确区分三个点：

1. 场景判定框几何中心；
2. Text Display 实体位置/变换原点；
3. 文本可视内容的对齐中心。

如果目标是使用用户指定的判定框中心，建议把统一锚点定义为：

```text
200.5, 67.0, -1.0
```

然后所有 Text Display 的相对位置都从该锚点计算，不再由 `66.0` 的旧基线和事件 `position.y=1.5` 叠加产生隐式偏移。

### 第二阶段：分别计算三轴边界

不要继续使用单一 `bounds` 生成正方形边界。应根据目标判定框的实际内边界计算：

```text
width  = 判定框右内边界 - 左内边界
aheight = 判定框上内边界 - 下内边界
depth  = 判定框前后内边界差值（若需要）
```

并明确 Minecraft 方块坐标是方块中心/方块边界哪一种参照，再加半格修正。Text Display 的 `displayWidth/displayHeight` 应表示实体的覆盖/裁剪范围，而不是简单等于文本长度。

### 第三阶段：再调整文字内容变换

当紫色实体边界已经和目标判定框几何范围一致后，再通过以下字段调整实际文字视觉位置：

- `position`：世界锚点偏移；
- `rotation`：固定朝向；
- `scale`：文字视觉大小；
- `lineWidth`：换行宽度；
- 文本对齐/背景/阴影等显示属性；
- 必要时使用 transformation 的 translation，而不是继续修改实体位置承担所有偏移。

## 不建议的表层修复

- 不建议只把 `TEXT_DISPLAY_CENTER_Y` 从 `66` 改成 `67`，因为事件默认 `position.y=1.5` 仍会继续叠加。
- 不建议只把 `displayWidth/displayHeight` 改成一个更大的固定数字；不同 laneCount、不同文本 scale 和不同结构尺寸下仍会错位。
- 不建议通过修改相机位置或截图透视来“伪装贴合”。
- 不建议把紫色实体包围框当成文字实际边界来调文字缩放。

## 交给实现方的验证任务

1. 输出当前 Text Display 的最终世界位置、`displayWidth`、`displayHeight`、scale、rotation、lineWidth、文本行数和事件 position。
2. 输出播放区青色结构的左右、上下、前后世界边界，并计算几何中心。
3. 用同一坐标系比较两者，不用截图像素直接反推。
4. 分别验证普通 `TEXT_DISPLAY`、`TEXT_DISPLAY_EFFECT` 的线性变换和 `HOLOGRAM`，避免只修一个事件类型。
5. 确认紫色框来自实体调试包围盒/显示边界还是其他调试渲染；若是调试包围盒，应记录其定义来源。
6. 在至少一个不同 laneCount、不同 scale 和多行文本场景下复核。

## 最终判断

当前最可能的根因是：`displayWidth/displayHeight` 使用了与场景无关的固定正方形计算，加上 Text Display 基准 Y 与用户判定框中心存在 1 格差异，并且事件相对 position 可能再叠加偏移。要实现真正贴合，必须先统一世界锚点和方块边界定义，再独立校准实体包围范围与文字视觉变换。
