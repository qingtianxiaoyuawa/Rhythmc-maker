# UI 彻底替换范围修订

- 日期：2026-10-01
- 用户补充：当前 UI 完全不符合预期，改造时尽量不要保留。
- 本记录修订此前 Flashback 风格 + Owo 渐进移除方案的保留策略；原方案的目标布局与最终移除 Owo 方向继续有效。
- Planner 边界：仅规划，不修改源码、不编译、不测试、不部署。

## 核心决策

将当前 UI 视为需要**整体替换的旧产品界面**，而不是需要逐页美化或延续的设计基础。新 UI 从 Flashback 截图和用户目标重新建立信息架构、布局、视觉规范和交互模型。不得因为当前页面类已存在，就要求新工作台继续采用其页面结构或视觉样式。

允许保留的是经确认仍有价值的非 UI 能力，不是旧 UI 外观或布局：

- 谱面、场景、轨道、音符、特效、播放和文件格式业务逻辑。
- 已验证的 Minecraft/ImGui 帧生命周期、最终 framebuffer 合成时序、GL 状态保护。
- 中文字体加载、字符输入、剪贴板、键盘映射等可独立复用的底层能力；迁移前仍需确认这些实现不与 Owo 类型耦合。
- 对用户有价值的功能行为、快捷键、校验、确认步骤和错误反馈；只迁移语义，不迁移旧控件布局。

旧 Owo 页面、FlowLayout/面板组合、居中窄表单结构、重复卡片和旧样式不作为新 UI 的实现模板。若其源码中混有必须保留的业务动作，应先提取/确认动作入口，再替换整个页面；不得为减少改动而把旧 UI 嵌进新工作台长期共存。

## 修订后的实施策略

### 1. 先冻结旧 UI 的功能清单，不做外观兼容

只盘点每个旧 Screen 的：用户可执行动作、读取/写入的数据、输入验证、快捷键、导航返回、错误/成功结果。忽略旧页面的尺寸、布局、组件树和视觉细节。产出“功能行为 → 新工作台位置/新模态窗口”的映射表。

### 2. 直接建立新的主工作台

新主入口直接切换到全屏工作台骨架：顶部菜单、中央场景预览、右侧检查器、底部时间轴，左侧栏默认隐藏。新工作台使用独立 Screen 与自有 ImGui 布局，不继承 RhythmcScreen/BaseOwoScreen，不调用旧页面面板 helper。

### 3. 新 UI 完整承接旧功能，旧页面随后删除

按用户任务流程而非旧类结构组织迁移：

- 工程/谱面：新建、打开、保存、谱面属性、最近文件。
- 编辑：对象/轨道选择、音符与特效属性、场景属性。
- 运输控制：播放、暂停、停止、跳转、缩放和播放位置。
- 场景：场景切换、导入、编辑、重置和删除确认。
- 输出：导入/导出配置、结果与错误反馈。
- 选择器：物品、文件和其他资源选择。

优先将这些功能做成新工作台中的菜单、检查器、轨道面板和统一模态窗口，而不是逐个复刻旧 Screen。功能可按阶段上线，但 UI 架构只设一套。

### 4. Owo 只允许短期迁移桥接，不作为最终或长期回退

由于旧入口存在大量 Owo 类型引用，迁移期间可短暂保留尚未切换的代码以便小步构建；但应设清晰删除批次和终止条件。不得将 Owo 页面作为新工作台的常驻弹窗、兼容模式或最终兜底。新建代码不再引入 Owo 包。

### 5. 业务与 UI 分层后，清理旧 UI

当某项功能由新 UI 调用既有业务服务且行为验收通过后，删除对应旧 Screen、旧控件和只服务于旧 UI 的 helper。全部入口迁完后，移除 `src/main/java/io/wispforest/owo/...` 携带源码及所有 Owo 类型判断/引用；不保留旧界面类作为回退实现。

## 明确不保留清单

除非源码审查证明其中某段属于不可替代的业务逻辑，否则新方案不复用：

- `RhythmcScreen` 的 Owo 页面继承体系和居中窄页面范式。
- `PlaceholderScreen` 的旧导航/表单布局。
- 旧 Screen 的组件树、嵌套 FlowLayout、固定尺寸面板和页面级滚动实现。
- 旧按钮/输入框/下拉框/弹窗的绘制与布局实现。
- 旧 UI 的颜色、边框、卡片、边距和控件密度。
- 以 `BaseOwoScreen` 为条件的键盘/鼠标转发逻辑。
- 作为长期双 UI 运行方案保留 Owo 或旧屏幕。

## 必须保留并重新接入的行为清单

- `.rmcc`、`.rmcd`、`.schem` 数据语义与读写兼容。
- Beat、BPM 分段、offset、播放和音频同步规则。
- 谱面创建/打开/保存/导入/导出和错误处理。
- 场景选择、编辑、重置/删除保护及其数据校验。
- 物品选择和特效配置的实际业务结果。
- 播放开始/暂停/停止、任意位置定位、播放失败清理与快捷键行为。
- ImGui/Minecraft 渲染注入时序、Framebuffer 与 GL 状态恢复。
- 中文/英文输入、完整 Unicode 字符事件、剪贴板、常用编辑键和焦点释放。

若某项旧功能已过时、重复或本身不符合目标，应先在规划/需求映射中标注并交由用户确认是否取消；不能因旧界面存在就机械地全部复刻。

## 更新后的执行阶段

1. **旧 UI 行为盘点**：只记录功能语义与业务调用，不做旧界面重构或修饰。
2. **新架构起步**：建立独立 ImGui Screen、工作台布局、主题、输入路由和统一模态层；主入口尽早切到新工作台。
3. **新流程优先实现**：按谱面工作流/场景工作流/导入导出工作流接入既有业务服务。
4. **按功能验收后删除旧代码**：每一组新流程可用后移除对应 Owo Screen 与专用组件。
5. **全量清理**：删除 Owo 源码、Owo 命名空间、Mixin/Screen Owo 判断、旧 UI helper 和仅供旧 UI 使用的资源。
6. **最终验收**：检查新 UI 完整性、数据兼容、输入和渲染行为；构建及运行时验收由实现/编译合作方执行。

## 新界面方向不变

- 顶部窄菜单栏。
- 中央大面积 Minecraft 场景预览。
- 右侧上下文检查器，按选择对象变化。
- 底部常驻时间轴、播放控制和轨道。
- 左侧对象/资源栏可选、默认收起。
- 深色低对比面板、细分隔线、紧凑控件、蓝色仅作状态/操作强调。
- 导入、导出、创建、资源选择和确认都使用同一套 Maker 自有模态 UI。

## 交给实现方的关键要求

- 不以“复用现有 UI”为目标；只复用经审查的业务服务和底层渲染/输入设施。
- 新工作台的组件和页面结构必须独立于旧 Owo UI 类。
- 迁移期不得让用户需要在新工作台与旧 Owo 页面之间来回操作完成一个常见流程；优先按完整用户流程一次迁移。
- 每删除一批旧屏幕，检查旧 Screen 导航、输入 Mixin、组件、资源和调用点均已断开。
- 最终删除 Owo 命名空间与源码，不保留隐藏开关、旧版入口或长期兼容 UI。
- 如果为降低单次风险需要短暂桥接，桥接只存在于开发迁移阶段，并在任务清单中明确负责人和删除阶段。

## 本轮结论

“尽量不进行保留”解释为：旧 UI 的视觉、布局、页面继承结构和控件实现原则上全部舍弃；只保留经确认仍正确的业务语义和底层 ImGui/Minecraft 渲染输入能力。新 UI 直接按 Flashback 风格工作台重新设计，Owo 只可作为短期迁移桥接，最终完全删除。
