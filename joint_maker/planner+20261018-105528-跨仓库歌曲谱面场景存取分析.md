# RhythMC 3.0 歌曲、谱面与场景存取链路分析

日期：2026-10-18 10:55:28（Asia/Shanghai）

## 范围与结论摘要

依据本轮提供的 Converter、Frontend、Reborn、Docs、Charter V2、Backend 六个源码包交叉分析。这里的“场景”按 Reborn 的 Arena（场景几何/显示配置）理解，不等同于歌曲谱面中的效果事件。

核心结论：歌曲元数据、谱面内容、资源包和 Arena 几何并非一个文件或一张表保存。谱面文件以 Reborn 兼容目录资产形式发布；歌曲/Arena 展示 manifest 是后端从数据库生成到 OSS 的投影；音频/材质等由资源包及资源清单分发；Arena schematic 是独立资产。Reborn 启动时同步资源至本地缓存，再用目录反序列化注册，选曲开局时才将谱面、Arena 和歌曲音频组装进 GameInstance。

## 一、分别保存什么

### 1. 歌曲元数据与难度谱面

- Reborn 读取目录约定为 `Data/Charts/<songId>/manifest.yml`，并可读取 `world.rmcc`、`nether.rmcc`、`end.rmcc`、`void.rmcc` 等难度文件。manifest 是歌曲展示和资源关联信息；每份 `.rmcc` 表示一个可选难度，数据根含 `meta`、`tracks`、`effects` 等谱面结构。
- `.rmcc` 的读取兼容两种编码：先尝试 Zstandard 解压后解析 JSON，失败再按普通 JSON 读取。因此扩展名本身不能证明文件必定压缩。
- Charter V2 的创作工程草稿使用 `.rmcd` ZIP，内部含 `draft.json`、`operations.ndjson`、快照及 assets 索引；它不是 Reborn 运行时谱面。编译器将草稿编译成 `manifest.yml` 和各难度 `.rmcc`，并生成 `compile-report.json`。
- Charter V2 编译结果在 `<songDir>/build/<draftId>/<revision>/` 下；这是本地编译产物，不代表已经上传到线上或进入游戏服务器资源库。

### 2. Arena 场景

- Arena 是独立于歌曲/谱面的场景资产：`Data/Arenas/<arenaKey>/metadata.yml` 描述名称、图标、材质等；`arena.schem` 保存 WorldEdit schematic 几何。
- 谱面难度 `meta.initialArena` 可以引用 Arena key，作为开局场景选择；它只是引用，不把场景几何嵌进 `.rmcc`。
- Converter 的 Arena 转换实现将旧 Arena 转换为 `arena-id/manifest.yml + arena.schem` 结构；当前 Reborn/Backend 对外契约使用 `metadata.yml`。因此转换器旧输出名与新运行时契约存在版本/格式边界，不能假设 Converter 产物可未经适配直接作为当前 Backend/Reborn 资产。

### 3. 音乐与资源包

- Backend 资源服务以资源 manifest 和对象存储文件索引管理资源；歌曲音乐通过 song id 关联资源包产物/哈希，Reborn 通过资源包管理器请求/校验包，再由游戏运行时播放 `music:s<song_id>`。
- 歌曲元数据的 `respack_sha1` 是对资源包版本/内容的引用信息，不是音频本体，也不是谱面 JSON。

## 二、保存、发布、同步、调用的端到端链路

```text
Charter V2 编辑
  ├─保存 .rmcd 草稿（可恢复编辑状态）
  └─编译 → manifest.yml + 难度 *.rmcc + compile-report
       ↓（运营/管理端发布；非本地编译自动上传）
管理端/Backend DB 与资源资产
  ├─songs、levels、collection_songs、arenas 等结构化记录
  ├─音频/资源包与 schematic 等对象资产
  └─GameDataManifestGenerator 生成 manifest.yml / metadata.yml 投影 → OSS
       ↓ 资源 manifest/hash 增量校验下载
Reborn 本地 Data/Charts、Data/Arenas 缓存
  ├─启动期目录加载、反序列化并注册 Chart/Arena
  └─选曲 → 选难度 → GameInstance 加载 Level/Arena、请求资源包、播放歌曲
```

注意，Backend 管理的数据库行、OSS 文件对象、游戏服本地缓存、Charter 草稿是四个不同持久化层。前端仓库的歌曲浏览/详情 API 主要服务社区展示与交互，不能将其等同于制谱工程文件写入 Reborn 目录；本次源码未找到“Charter V2 保存后自动直传 Backend 并部署进 Reborn”的闭环。

## 三、Reborn 加载和游玩调用

1. `ConfigManager.initData()` 从本地 `Data/Charts` 和 `Data/Arenas` 读取目录并调用对应 deserializer，创建内部 RawSong/RawLevel/Arena 模型，注册到管理器。缺少有效 manifest 或谱面文件时相应内容无法正常注册。
2. 在线数据权威化方案中，Backend `GET /server/charts` 给出活动谱面目录及歌曲展示字段，`GET /server/arenas` 控制活动 Arena 注册；资源管道按 SHA-256 校验、增量下载文件资产。离线时 Reborn 使用本地上次同步的投影文件。
3. 玩家选歌并选择难度后，GameManager 创建 GameInstance；实例使用谱面及其 `meta.initialArena`（若无则回退默认 Arena），加载 Arena schematic/实例化场景。
4. GameInstance 按 song id 请求资源包；音乐资源可通过 `music:s<song_id>` 标识播放。音符、轨道和 effect 则从所选难度 `.rmcc` 的数据进入运行时播放逻辑。
5. 运行时 Arena effect 可触发 Arena 切换/替换当前场景实例；这属于播放过程中的引用调用，不是修改或重新保存 Arena 文件。

## 四、重要的源间差异与风险

- **草稿≠可玩谱面**：`.rmcd` 是 Charter V2 自己的可编辑容器，只有编译产物符合 Reborn `manifest.yml + *.rmcc` 契约后才可作为运行输入。
- **本地编译≠线上发布**：Converter/Charter 编译只写本地目录。发布还需将谱面文件、资源包、音频等资产送入管理/Backend/对象存储流程，并更新数据库/活动目录及 manifest 投影。
- **manifest 的权威角色变更**：Docs 记载旧流程由运营手工维护并上传 manifest；当前方案由 DB 为权威、Backend 确定性生成 YAML 投影到 OSS。故不应把 manifest 当成新版线上主数据源。
- **Arena 双组件**：数据库/metadata 描述 Arena 的注册与展示；`arena.schem` 才是空间结构。只上传 metadata 不足以呈现场景，只上传 schematic 也不保证可注册或可被谱面引用。
- **工具格式漂移**：Converter 的 Arena 输出文件名是 `manifest.yml`，而 Docs、Backend 与 Reborn 目标格式是 `metadata.yml`；必须确认转换版本或部署适配层，不可凭旧转换器结构直接导入。
- **Frontend 角色边界**：本轮 Frontend ZIP 中可见社区 Web 前端和服务端 API 模块，但没有证据证明它承载 Charter V2 制谱工程保存或 Reborn 服务器部署。线上上传的具体管理端流程需以 Backend Web Admin/Redis Bridge 与部署配置为准。
- **源码快照边界**：以上结论针对用户提供 ZIP 的快照。没有对线上运行环境、OSS 实际对象、管理端配置或真实服务器目录做访问验证；部署状态不能单凭源码推断。

## 五、供后续实现方使用的对接清单

1. 统一运行时导出契约：`Data/Charts/<songId>/manifest.yml` 与每难度 `.rmcc`；文档说明并校验 Zstd 与 plain JSON 的兼容性，建议新产物固定一种编码并有回读测试。
2. 保留 `.rmcd` 为编辑项目/自动保存格式；将“保存草稿”“编译运行时文件”“上传发布”设计成显式分离的状态与操作，不能将编译成功误报为线上发布。
3. 发布谱面时校验 song id、难度文件名、`meta.uid`/难度映射、track/effect schema、`initialArena` 引用及 manifest 字段，再进行 Reborn 回读验证。
4. 发布 Arena 时将 metadata/数据库注册信息与 `arena.schem` 作为一个有一致性校验的发布单元，并检查所有谱面 `initialArena` 与 ARENA effect 引用均存在且活动。
5. 资源包更新后同步更新资源 hash/manifest 投影，确保音乐 `music:s<song_id>` 对应的资源真实存在；缓存需按 SHA-256 更新且保留断网可用副本。
6. 为端到端验收建立样例：Charter 草稿保存→编译→上传发布→Backend/OSS 资产与清单→Reborn 同步缓存→加载指定难度/Arena→音乐/谱面/effect 实际调用；记录每一步产物 hash 和版本。
