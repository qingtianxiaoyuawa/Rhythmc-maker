# RhythMC Maker 谱面崩溃优化方案

- 日期：2026-10-03 14:20:18（Asia/Shanghai）
- 身份：Planner；本轮不修改源码、不编译、不测试、不部署。

## 优化目标

在不改变现有制谱逻辑和播放逻辑的前提下，解决谱面文件被截断导致的崩溃，同时避免保存、校验和刷新给制谱器带来卡顿。

## 推荐方案

### 1. 保存链路：临时文件 + 原子替换

- 所有谱面保存先写入同目录临时文件，例如 .chart.tmp。
- 写入完成后执行 JSON 完整性校验，再关闭文件句柄。
- 校验通过后使用原子替换更新正式文件；校验失败或写入中断时删除临时文件，保留旧文件。
- 不直接对正式谱面文件执行覆盖写入，避免客户端读到半成品。
- 临时文件名应带唯一后缀，避免多个保存任务互相覆盖。

### 2. 数据保护：保留上一份有效副本

- 正式文件替换前保留 .bak 或带时间戳的历史副本。
- 只保留有限数量的历史副本，避免无限增长。
- 启动或刷新时，正式文件解析失败则按“正式文件 → 最近有效备份”顺序恢复。
- 恢复前再次校验备份，不能仅按文件存在判断有效。

### 3. 刷新链路：失败隔离，不阻断客户端 Tick

- efreshActiveChartIfChanged 不应让 JSON/IO 异常穿透 END_CLIENT_TICK。
- 解析失败时继续使用内存中的最后有效谱面，不清空当前编辑状态。
- 同一个损坏文件在未发生变化前只提示一次，避免每 Tick 重复解析和刷屏。
- 文件修改时间、大小或哈希发生变化后才允许再次尝试解析。
- 错误提示包含谱面路径、错误行列、备份恢复状态和建议操作。

### 4. 性能优化：异步解析 + 主线程短提交

- 文件读取和 JSON 解析放到后台任务，不能在客户端 Tick 中同步执行。
- 后台任务只生成不可变的候选谱面快照，不直接修改游戏状态。
- 主线程只在候选快照校验成功后，用一次短操作替换活动谱面引用。
- 同一文件同时存在多个刷新任务时，只保留最新任务，取消或丢弃旧任务结果。
- 保存任务使用串行队列，防止多个线程同时写同一谱面。

### 5. 版本一致性：避免旧结果覆盖新结果

- 为每次保存和刷新分配递增序号或文件版本号。
- 后台解析结果提交前检查序号；旧任务结果不得覆盖更新后的谱面。
- 保存开始后若文件已被外部修改，应重新读取或拒绝覆盖，并提示用户。

## 不推荐的处理方式

- 只用 	ry-catch 吞掉异常：只能防崩溃，不能防数据损坏。
- 每 Tick 重新读取和解析完整 JSON：会增加卡顿，且无法解决写入竞争。
- 直接删除损坏文件：可能丢失用户谱面，且无法追溯恢复。
- 只依赖文件大小和修改时间：同大小快速替换时可能漏检，建议结合保存序号或文件哈希。
- 在主线程执行完整 JSON 校验：大谱面会造成操作响应延迟。

## 推荐实施顺序

1. 先实现保存原子性，阻断新损坏文件产生。
2. 再实现活动谱面刷新异常隔离，阻断客户端崩溃。
3. 增加最后有效快照和备份恢复，处理已有损坏文件。
4. 将解析和校验移到后台线程，消除大谱面刷新卡顿。
5. 最后增加版本序号、取消旧任务和回归验证。

## 验收标准

- 保存过程中强制中断不会产生可被读取的半截正式文件。
- 截断 JSON 被读取时客户端不崩溃，仍保留最后有效谱面。
- 正式文件损坏时可恢复最近有效备份，并明确提示用户。
- 连续快速保存不会出现旧任务覆盖新谱面。
- 大谱面刷新不阻塞制谱器操作响应。
- 同一损坏文件不会在每个客户端 Tick 重复解析或重复弹错。
