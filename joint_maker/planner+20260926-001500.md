# 导入 3.0 谱面后音符消失诊断

- 时间：2026-09-26 00:15:00 +08:00
- 用户反馈：导入谱面后播放时音符消失
- 当前阶段：仅诊断，未修改源码，未编译

## 当前工程进度

- 3.0 分文件导入界面已存在：难度文件、谱面信息、歌曲文件、场景。
- 导入难度文件后会读取 `.rmcc` 的 `meta`、`tracks[].notes` 和 `effects`。
- 完整场景会保存到 `rhythmc maker/scenes/<chart-id>/initial` 或 `scene<n>`，并尝试安装到播放/场景编辑区域。
- 最近一次编译记录显示导入场景已接入 `.schem` 解析和方块写入，但没有进行实际游戏内播放回归。
- 音符消失问题应优先检查谱面数据转换和播放时钟，不应先归因于场景。

## 主要根因

`ChartStorage.importRhythmc3()` 第 86 行只把 3.0 音符的 `beat` 写入 `ChartManifest.Note`，没有写入 Maker 播放逻辑依赖的 `note.time`。

本地制谱创建音符时明确执行：

```java
note.time = note.beat * 60.0 / chart.bpm;
```

但导入路径没有同等转换。因此 Java double 默认值为 `0.0`，所有导入音符的 `time` 都变成 0。

播放路径依赖：

- `PlaybackSession` 按 `note.time` 排序；
- `effectiveNoteTime(note, chart)` 返回 `note.time + offsetMillis / 1000.0`；
- 播放循环在 `noteTime <= songTime` 时回收音符；
- 初始化时还会把 `effectiveNoteTime(note) < startSeconds` 的音符直接加入 `hitNotes`。

所以导入后会出现：

1. 所有音符被认为发生在歌曲开始附近；
2. 若 Offset 为负数，音符启动时就已过判定时间，直接被标记命中并回收；
3. 若 Offset 为正数，所有音符也共享同一个时间，只会在同一时刻集中出现/消失；
4. 播放时不会按照 `.rmcc` 的 beat 分布流动。

## 必须修复的转换

导入每个 note 后至少要计算：

```text
note.time = note.beat 对应的歌曲秒数
```

如果当前模型暂时只支持单 BPM：

```text
note.time = note.beat * 60.0 / firstBpm
```

更正确的 3.0 兼容实现应根据 `meta.bpms[]` 分段积分，把 beat 转为秒：

```text
beat 0..BPM 节点1 使用前一段 BPM
超过 BPM 节点后使用新的 BPM
```

注意：`offset` 已在 `effectiveNoteTime()` 中统一加入，不应在导入时再次加到 `note.time`，避免重复偏移。

## 第二个重要问题：BPM 变化被丢弃

当前导入只读取 `meta.bpms[0].bpm` 写入 `chart.bpm`，没有保存完整 `meta.bpms[]`。

这会导致：

- 变速谱面的后续音符时间计算错误；
- 导入后播放速度与原 3.0 谱面不一致；
- 当前 `distanceAt()` 也只用 `chart.bpm` 将秒换算为 beat；
- 3.0 的 BPM 节点不能被完整还原。

应新增 BPM 变化模型，例如 `BpmEvent(startBeat, bpm)`，并让：

- beat → seconds 使用分段积分；
- seconds → beat 使用反向分段查找；
- 播放距离、特效时间、谱面结束时间使用同一 timing 模型。

## 第三个问题：导入字段语义混用风险

3.0 Note 的 `pos` 是轨道内空间坐标 `[x, y, z]`；Maker 当前 `ChartManifest.Note.z` 同时承担编辑器轨道位置/时间轴方位的历史职责。

当前导入代码把 3.0 `pos[2]` 直接写入 `note.z`，但播放位置的前后移动实际上由 `note.time` 和 `displayZ` 计算，不应把 3.0 的空间 z 当作播放时间。

需要明确：

- `beat`：时间位置；
- `pos[0..2]`：音符空间位置；
- Maker 编辑器的内部轨道坐标：如果与 3.0 坐标不同，应单独转换或新增字段；
- 不能用空间 z 替代 beat/time。

这不是当前音符立即消失的首要原因，但会造成导入后音符位置异常或重新保存时数据失真。

## 其他导入兼容问题

- 当前 `.rmcc` 导入直接读取纯文本 JSON，未实现 Zstd 解压；压缩 3.0 文件可能无法导入。
- 当前 `meta.initialArena` 没有写入 `ChartManifest` 或导入绑定模型，场景引用可能无法准确对应。
- 当前导入 effects 原样保存，但场景引用与场景资源没有按 effect 的 `arena` key 建立绑定。
- `manifest.yml` 解析使用简单逐行 `startsWith`，复杂 YAML、转义或多行文本可能读取错误。
- 音频文件只用于保存和时长读取，不能修复音符 timing；3.0 timing 应始终来自 `.rmcc`。

## 排查优先级

P0：导入后为每个 Note 生成正确的 `time`，并用第一个 BPM 验证固定 BPM 谱面音符顺序和消失时机。
P0：增加导入日志或诊断信息：音符数、最小/最大 beat、最小/最大 time、BPM、Offset。
P1：保存完整 `bpms[]`，实现变 BPM beat/秒互转。
P1：明确 3.0 `pos` 到 Maker 编辑坐标的转换，避免直接复用历史 `z` 字段。
P1：支持 Zstd `.rmcc`。
P2：完成场景引用绑定和实际游戏内回归。

## 最终判断

当前“音符消失”的最高概率根因是：

```text
导入时只设置 note.beat，没有设置 note.time；
播放系统按 note.time 判定，导致所有音符被当成 time=0。
```

场景导入问题是独立问题，通常不会让音符的时间全部归零。
