# 正式播放音画偏差与编辑卡顿诊断规划

- 日期：2026-10-01
- 用户报告：
  1. 正式播放出现严重音画不同步；滚动播放白框移动、音符运动与音乐对应存在明显偏差。
  2. 制谱器帧率稳定，但操作像线程/游戏 Tick 受阻，出现类似多人服务器网络延迟的卡顿感。
- 当前实现基线：`maker+20261001-094019.md`、`maker+20261001-095804.md`、`maker+20260930-235900.md`。
- Planner 职责：只分析、诊断和规划；不修改源码、不编译、不测试、不部署。
- 证据限制：用户本轮未提供最新运行日志、卡顿发生时操作步骤、具体延迟量或性能采样；下列根因是源码路径支持的高优先级假设，不冒充已由运行实测确认。

## 已确认的实现事实

### 客户端播放时钟

- `RhythmcMakerClient.beginPlayback(...)` 在开始处理播放时先设置 `playbackClockStartedAtNanos = System.nanoTime()`。
- 随后设置 pending server command 并调用 `startAudio(startChunk)`。
- `startAudio(...)` 若内置播放器仍在异步准备，会直接返回；正式播放命令会暂存到后续 `END_CLIENT_TICK`，等播放器启动或确认失败后才发送。
- 音频进程创建后才设置 `audioStartedAtNanos = System.nanoTime()`。
- 滚动播放白框选择 `playbackClockStartedAtNanos` 优先于 `audioStartedAtNanos` 计算 elapsed，因此启动等待期间白框时钟已经前进；一旦播放器准备耗时不为零，白框有可能从音频播放位置之前/之后偏移。

### 服务端播放时钟

- 客户端发送 `rhythmc_play` 后，服务端建立 `PlaybackSession`，其 `startNanos` 设为当前单调时钟再加 `PLAYBACK_START_DELAY_TICKS * 50ms`。
- 服务端在到达 startNanos 后以服务器 `System.nanoTime()` 推进 `songTime`。
- 正式音符触发、正式模式音符实体位置和特效事件均以此服务器 songTime 判定。
- 因而客户端播放器进程启动时间与服务端固定延迟后的播放时间不是同一确认事件；Minecraft 命令传输/派发延迟和外部 ffplay 音频输出缓冲也未形成共同时间基准。
- 白框是客户端世界渲染事件中的独立估算时钟，正式模式音符/特效由服务端时钟驱动。当前架构存在至少两个时钟源，不能保证天然同步。

### 卡顿相关路径

- 服务端 `processPlaybackSessions(...)` 在 Server Tick 中更新活动 BlockDisplay、逐个计算位置、处理命中音效、播放特效并扫描待预载音符。
- 正式模式对实体位置更新有 Tick 间隔控制，创建显示实体也有每 Tick 数量/活动量限制；但活动实体遍历、属性更新、scoreboard glow team 更新等仍可能产生随活动实体量增长的主线程工作和网络同步。
- `PlaybackSession` 建构会复制并排序 notes/effects、为所有音符准备时间/距离映射；如果在命令处理主线程构建大谱面，会形成启动尖峰。
- 客户端 `END_CLIENT_TICK` 每 Tick 调用 `updateEditorSidebarSnapshot(...)`，其中解析活动谱面；其访问链可能读取集成服务器状态/存储。是否造成卡顿需用耗时采样确认。
- 记录 `maker+20261001-095804.md` 表明最近 UI 改造仍基于普通 Owo 页面；UI 帧率稳定并不能证明客户端 Tick、集成服务端 Tick、渲染线程或网络派发无阻塞。
- “多人服务器网络延迟感”是体感描述，不足以证明真实网络延迟。若用户处于单人/集成服务器，优先检查主线程 Tick、区块加载/保存、数据包排队和 GC；若处于远程服，再追加 RTT 与服务端 MSPT 采样。

## 高优先级根因假设

### A. 播放同步：起点和时钟没有统一（高优先级）

- 播放白框时钟在播放器准备/音频启动之前建立；服务器 session 又有固定 3 Tick 延迟；ffplay 实际音频输出存在独立启动缓冲。
- 这会造成客户端显示时间、客户端音频位置、服务端音符/特效时间彼此偏移。
- 对“严重”偏差而言，启动延迟能够解释固定起始偏移，但若偏差随播放持续扩大，还需检查 playbackRate、采样率/tempo filter、媒体 seek、服务端 Tick 丢帧后是否 wall-clock 追赶、BPM 分段和 offset 的边界。
- 必须区分“固定偏移”和“随时间累积的漂移”，两者根因不同。

### B. 播放跟随主线程/服务器墙钟（高优先级）

- 服务器 songTime 由真实单调墙钟计算，而实体更新只在 Server Tick 执行；当 Tick 卡顿时，下一次处理会直接跨过一段 songTime。
- 命中/特效可能在恢复后的同一 Tick 批量触发，实体位置也可能跃迁；帧率读数未必同步显示游戏 Tick 被阻塞。
- 客户端滚动白框同样由墙钟估算，实际渲染帧停止时无法绘制；恢复后位置直接跳跃。白框和服务器对象可能以不同采样/更新节奏跳动。

### C. 编辑操作卡顿：Tick 主线程或同步数据操作（中高优先级）

可能来源包括：

- 大谱面 `PlaybackSession` 初始化、排序和全音符映射准备。
- 每 Tick 活动显示实体/Scoreboard 处理与相关数据包同步。
- 同步保存、谱面状态解析、区块加载或场景处理。
- 客户端 UI 绘制/布局每帧重建过多控件，或字体/纹理上传等一次性尖峰。
- GC、JIT、外部音频进程/磁盘 I/O。

目前没有采样数据，不能只凭“FPS 稳定”排除或锁定任何单一来源。

## 需要实现方先采集的最小证据

1. 标注测试环境：单人集成服或远程服务器、游戏分辨率/GUI 缩放、模组数量、谱面 note/effect 数、播放速率、正式/滚动模式。
2. 同一段固定谱面分别测正式和滚动播放，记录播放开始、音频实际起声、白框经过指定 Beat、首个对应音符命中/显示的时间。
3. 比较播放开始处与中段偏差：固定偏移表示启动锚点问题；偏差随时长增长表示 rate/时间映射/累计误差问题。
4. 记录 Minecraft client tick 与 integrated/dedicated server tick 的单 Tick 耗时、p50/p95/max；单独埋点 `processPlaybackSessions`、session 构建、每 Tick 实体更新和 UI 屏幕操作。
5. 记录每 Tick 活动显示实体数、实体创建/复用/移动数、命中/特效事件数、待处理命令数；记录 GC pause 和音频进程启动时刻。
6. 如果是远程服务器，再独立记录网络 RTT/包处理延迟；不能把 Tick 停顿一概归因于网络。

## 修复规划

### 第一阶段：统一播放时钟与同步协议

- 确立单一权威时间线和明确的“共同开始时刻”。建议在 ffplay 进程创建成功后，由客户端取得启动时刻，再将同一绝对目标开始时间/同步 nonce 交给服务端；服务端确认采用后，客户端和服务端均从该共同单调时刻计算 chart time。
- 不得用“客户端发命令时刻 + 固定 3 Tick”代替对共同起点的确认，除非实测证明确认时延并有同步补偿。
- 滚动白框必须读取同一个播放状态/时钟锚点，不在 `beginPlayback` 过早启动一个独立计时器。
- 播放器准备失败时不启动白框/服务端会话；音频进程退出、取消或停止时三者一致清理。
- 评估 ffplay 能否暴露/获取真实媒体播放位置或音频设备输出延迟；如果不可用，记录已知启动偏差并建立补偿策略，而不是假设 `ProcessBuilder.start()` 等于扬声器出声。
- 在同步协议实现前避免同时保留多个含义不清的 `playbackClockStartedAtNanos`、`audioStartedAtNanos` 和 server start delay。

### 第二阶段：确认 rate 与时间映射

- 用 0.5x、1x、2x 播放同一测试谱面，检查 30 秒/60 秒偏差是否线性增长。
- 确认 ffplay tempo filter 的有效变速与服务端 session.rate 完全一致；滤镜算法改变音高/保调行为时也需验证时长。
- 选含 BPM 变化、非零 offset、分数 beat 的谱面，比较音符判定、音符视觉位置、白框位置和特效触发使用的同一个 ChartTiming 映射。
- 明确 `durationSeconds`、offset 和起始 chunk/beat 的包含边界，避免首拍重复或整体偏移。

### 第三阶段：消除 Tick 长帧和编辑阻塞

优先按采样定位，不做猜测式重构：

- 将谱面复制、排序、纯 Java 时间映射预计算等不触碰 Minecraft world/entity 的工作移出关键 Server Tick；通过安全的主线程切换提交结果。
- 控制每 Tick 音符实体创建、活动实体变换、特效执行和包发送的预算；预算必须防止单 Tick 无上限工作，同时不能因积压造成音画越拖越慢。
- 对实体和 Scoreboard 做批量/差量更新，避免每个音符每 Tick 重复执行不变的 glow/team 注册。
- 对大谱面考虑预计算索引和时间窗口查询，避免所有播放事件在启动时同步排序或每 Tick 从头扫描。
- 将磁盘保存、文件解析和大型场景操作从渲染/Tick 热路径移开；异步部分不得直接访问不线程安全的 Minecraft world、entity 或 registry 对象。
- UI 稳定帧率不代表输入及时：测量客户端 Tick 回调、鼠标/键盘事件到处理的时延和 UI 单帧 CPU 时间。

### 第四阶段：回归验证

- 空闲、普通谱面、大型谱面分别验证操作延迟。
- 正式模式和滚动模式分别比对音频、白框、音符实体、音效和特效。
- 从头播放和非零 Chunk 起播均测试。
- 变速、BPM 变化、offset、seek/停止/重播和播放器启动慢/启动失败均测试。
- 同步重点观察前段、中段和末段，分别捕捉固定偏移和累计漂移。

## 验收标准

### 音画同步

- 起播时音频、服务端音符/音效、特效时间和滚动白框使用同一有效时间锚点。
- 1x 播放固定谱面时，首段、中段、末段偏差不持续扩大；偏差阈值由实现方基于音频设备/服务器 Tick 实测给出，建议目标不超过 50–100 ms，并解释无法达到时的硬件/网络边界。
- 变速时客户端音频时长与服务端时间推进率一致。
- 从非零 Chunk 起播时，起始位置及 offset/BPM 分段计算正确。

### 卡顿

- 游戏 FPS 与 client/server tick 耗时分别报告，不能只报 FPS。
- 交互操作期间不存在可复现的长 Tick/主线程尖峰；报告 p50/p95/max tick time 和最大输入响应时延。
- 大谱面预载不会产生集中数秒卡顿；实体更新/事件触发有上限和积压策略。
- 播放停止/失败仍幂等清理服务端 session、显示实体、音频进程和白框时钟。

## 交给实现方的任务清单

1. 先补充远程/集成服、播放模式、谱面规模、偏差是固定还是累积等测试信息；同时加入低侵入耗时与时间戳采样。
2. 优先审查并统一 `beginPlayback`、`startAudio`、`rhythmc_play`、`PlaybackSession.startNanos`、白框时钟的启动协议。
3. 确保播放器启动成功后才建立/确认共同播放时刻，去掉无证据的固定起点错位。
4. 比较客户端、服务端和 ffplay 的有效播放进度，验证不同 playbackRate 与 BPM/offset。
5. 用 Tick p95/max 和方法耗时定位线程受阻源，再针对实体、I/O、UI 或 GC 采取最小修复。
6. 构建/运行由实现方执行并留 maker 记录；Planner 不执行修改、构建或运行验证。

## 本轮结论

源码可确认存在多套时钟和起播锚点不一致风险：白框时钟早于音频进程启动，服务端又在命令到达后延迟 3 Tick 才起播。该设计足以解释固定起播偏差，但是否是用户所见“严重偏差”的全部原因仍需时间戳对照。帧率稳定而操作发卡更应先检查 client/server Tick 长帧、主线程同步工作、数据包排队和 GC，而不是只看渲染 FPS。应先测量并统一播放时间锚点，再依据 Tick 耗时采样修复卡顿。
