# 本轮诊断记录

## 用户问题
播放谱面时所有音符同时出现，并同时加载几千个实体，最终导致游戏进程卡死。

## 当前播放链路
1. `RhythmcMaker.togglePlayback(...)` 创建 `PlaybackSession`。
2. `processPlaybackSessions(...)` 每个服务端 tick 计算 `songTime`。
3. 正式播放先处理已有显示实体，再从 `nextNoteIndex` 顺序扫描未来音符。
4. 新音符只有在：
   `relativeDistance(note, songTime) <= PLAYBACK_APPROACH_DISTANCE`
   时才创建 `BlockDisplayEntity`。
5. `PLAYBACK_APPROACH_DISTANCE = 25.0`。
6. `PlaybackSession.acquire(...)` 每个未复用显示实体都会执行 `world.spawnEntity(display)`。

## 根因
- `PlaybackSession.relativeDistance(...)` 使用：
  `track.distanceAt(note.beat) - track.distanceAt(currentBeat)`。
- `TrackPlayback.Prepared.distanceAt(...)` 遍历该轨道的 speed 数值事件；当轨道没有 speedEvents 时，事件列表为空，方法返回初始值 `0.0`，而不是默认的 Beat 距离。
- 因此无 speedEvents 的普通谱面中：
  `relativeDistance = 0 - 0 = 0`
  对所有未来音符都成立 `0 <= 25`。
- 音符虽然按时间排序，但距离窗口失效；播放开始后第一次处理就会从 `nextNoteIndex` 扫过几千个音符，并为每个创建一个 BlockDisplay。
- 这不是 HUD 刷新问题，也不是音频播放本身导致；是正式播放实体预加载窗口的距离计算退化。

## 相关位置
- `src/main/java/cn/frkovo/rhythmcmaker/RhythmcMaker.java`
  - `processPlaybackSessions(...)`：约 1775 行，实体生成窗口在 1813–1828 行。
  - `PlaybackSession.relativeDistance(...)`：约 2110 行。
  - `PlaybackSession.acquire(...)`：约 2145 行。
- `src/main/java/cn/frkovo/rhythmcmaker/chart/TrackPlayback.java`
  - `Prepared.distanceAt(...)`：无 speed 事件时返回 0。
  - `events(...)`：没有事件时返回空列表。

## 最小根修复
推荐让 `TrackPlayback.Prepared.distanceAt(beat)` 的空 speed 曲线使用默认单位速度：

```text
无 speedEvents：distanceAt(beat) = beat
有 speedEvents：按事件积分，并明确事件之前/之后的默认速度语义
```

这样正式播放开始时，未来音符按 Beat 距离进入窗口，不会全部满足距离条件。

更稳妥的兼容实现是：
- 若该轨道没有 speedEvents，回退到 `PlaybackDistance.Prepared.atBeat(beat)`；该类当前空事件时已经返回 `beat`。
- 或让 TrackPlayback 接收显式默认值，并在空事件时返回 `beat`。
- 不建议简单把生成条件改成 `noteTime - songTime <= 常量`，因为 speedEvents 会改变音符的视觉流速；应修复统一距离模型。

## 必须增加的保护
即使修复距离模型，也应增加防卡死保护：
1. 每 tick 最多创建固定数量的显示实体，例如 32/64 个；剩余音符留到下一 tick。
2. 生成前拒绝非有限距离：`NaN` 或无穷值不得被当作窗口内。
3. 生成前增加未来时间窗口上限，避免距离曲线异常时全量加载。
4. 对单个播放会话设置最大活动显示实体数量；达到上限时暂停继续预加载，优先回收已命中/离场实体。
5. 启动播放时输出一次诊断信息：总音符数、`nextNoteIndex`、首个未生成音符相对距离、活动显示实体数；不要每 tick 打印。

## 额外发现
- `PlaybackSession` 构造函数中计算了 `noteDistances`，但当前 `relativeDistance(...)` 没有使用该缓存；可以改为缓存“音符绝对轨道距离”，再减去当前距离，减少重复曲线积分，但这是性能优化，不是本次根因。
- `trackProfiles` 对每个轨道都建立 `TrackPlayback.Prepared`，并为轨道 0 提供默认对象；如果音符没有匹配轨道，也会走轨道 0 的默认距离逻辑。
- `stopPlayback(...)` 会清理会话中的显示实体和池，但无法挽救单 tick 内创建数千实体造成的服务器/客户端卡死，所以必须先修复生成窗口并限制单 tick 预算。

## 验收标准
- 无 speedEvents 的大型谱面开始播放时，第一 tick 只生成位于 25 距离窗口内的音符，不生成整张谱面。
- 生成数量随播放时间逐步增加，活动实体数保持在可控范围。
- 有 speedEvents 的谱面仍按 Track 距离预加载，不被简单时间窗口替代。
- 空曲线、NaN、负距离和异常 speedEvents 不会导致全量生成。
- 32/64 个实体的单 tick 生成预算可避免单次主线程长时间阻塞。
