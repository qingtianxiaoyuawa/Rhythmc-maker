# 本轮规划记录

## 用户问题
是否可将 RhythMC Maker 的音符 Beat 反算为最接近的 Chunk 内格位，并重新绑定至“每 Chunk 分数为 D、Chunk 内第 k 格”的位置，避免浮点近似造成音符位置漂移。

## 结论
可以。对确定由 Maker 网格放置的音符，保存整数全局格位 `gridIndex`（或 `chunkIndex + slotIndex`）作为权威位置；Beat 只作为导出到 RhythMC 3.0 `.rmcc` 的派生 double 值。这样导入 Maker 自己导出的谱面时，可从标准 double beat 还原最接近的格位，再以整数格位恢复编辑位置。

## 公式
设每 Chunk 格数为正整数 `D`，3.0 beat 为 `b`：
- 全局格位：`g = round(b * D)`
- 绑定后的 Maker beat：`b_grid = g / D`
- 以 1-based chunk 显示时：`chunk = floor(g / D) + 1`
- Chunk 内 0-based 格位：`slot = g mod D`
- 若界面显示“第几格”（1-based）：`slotDisplay = slot + 1`

例：`D=12`、`b=9.583333333333334`：`g=115`，对应 Chunk 10 的 0-based 格位 7（人类从 1 数第 8 格），恢复 beat 为 `115/12` 的 double 表示。

## 适用边界与安全策略
- 仅对明确来自 Maker 网格、且导出时使用相同 `D` 的音符执行网格还原。
- 不能对所有外部 3.0 谱面无条件吸附：外部谱面允许任意小数 beat，吸附可能改变作者原意。
- `.rmcc` 本身不包含 Maker 的每 Chunk 格数 `D`，因此只凭 `.rmcc` 无法可靠知道应使用哪个 D；Maker 项目/`.rmcd`/旁车状态需保留 `D` 与网格来源标记。
- 若用户把导入谱面 D 改成另一数值，不能拿新 D 盲目还原原格位；需要“导出所用 D”或明确的网格配置。
- 对没有 Maker 来源标记的文件，提供显式“按当前 D 吸附到 Maker 网格”操作，并显示预览/差异；不应静默量化。
- 最近邻总能找到某格，但这不意味着原 beat 一定属于该格。应验证误差 `abs(b - b_grid)` 小于只覆盖 JSON double 往返误差的阈值；超出时保留原始外部 beat，不吸附。阈值应通过实际 Gson/Fastjson 往返测试确定，而非用半个格距作为阈值。

## 推荐数据模型
- 网格创建的 Maker 音符：保存整数 `gridIndex`（可由 chunk/slot 组合），`D` 保存于 Maker 工程数据。
- 3.0 导出：`beat = gridIndex / (double) D`，写标准 JSON number，不改 `.rmcc` 结构。
- 导入：先保留 `sourceBeat`；只有明确是 Maker 导出且 D 可确定时，计算最近 gridIndex 并校验误差；校验通过后从 gridIndex 恢复编辑位置。
- 时间：由 beat 单向换算为播放时间，不得再从 time 反算并覆盖 beat/gridIndex。

## 验收建议
覆盖 D=4、12 等设置、不同 Chunk 边界、首尾格、跨 Chunk 舍入、3.0 JSON 写出/读入往返、变 BPM 与非零 offset。验证同一 Maker 谱面导出再导入后 `gridIndex` 完全一致，Beat 的 double 往返误差不会造成编辑位置变化；同时验证未标记的外部 3.0 小数 beat 不被自动修改。
