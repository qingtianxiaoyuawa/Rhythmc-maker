# Maker 场景编辑与示例 MOD 场景系统对比方案

## 项目范围

本轮只分析与规划，不改源码、不编译、不运行测试。分析对象为 Maker 本地工程与用户指定的 `RhythMC-MOD-0.5.1-beta.3.jar`。MOD 二进制的 UI/结构通过 JAR 元数据、类签名和 Java 21 javap 字节码检查；没有 MOD 源码，因此只描述可以确认的职责与数据结构，不推断未反编译到的行为细节。

## 当前 Maker 的场景编辑模型

Maker 的 SceneEditScreen 是 Owo 表单式菜单，主要功能是场景列表、新建、名称、图标、保存状态、重置、删除和开始搭建。真正的编辑不是屏幕内场景画布，而是传送玩家到世界中一个独立的建造区域，玩家用 Minecraft 方块直接搭建；物品栏按钮“保存场景”触发快照并返回制谱器。

场景元数据目前是 chart-scoped 的 `Scene`：索引、initial 标志、内部 name、displayName、icon、区域中心 X、saved、sceneId。结构作为 `arena.schem` 保存。`SceneEditStorage` 以本地目录和元数据文件读写，并有缓存/旧目录迁移逻辑；导出/播放时通过 `scene-editor:<index>` 绑定读取结构文件。

场地固定尺寸为 128×128×128，即 2,097,152 个方块位置。创建/重置清理按每 tick 4096 个格子推进；快照按每 tick 8192 个格子扫描；理论上遍历下限分别约 512 tick 与 256 tick（约 25.6 秒和 12.8 秒，按 20 TPS 且不含区块加载、方块访问及磁盘写入）。保存扫描覆盖整个固定区域，包括大量空气/空白，因此当前主要深层风险是固定大边界带来的 server-thread 方块读写和 `.schem` 冗余，而不只是 UI 外观。每 tick 预算只限制处理数量，不直接保证预算内耗时稳定。

## 示例 MOD 可确认的场景/竞技场能力

该包不止一个“场景设置表单”。存在 ArenaEditorScreen 分页编辑界面、ArenaPreviewRenderer 世界内参考预览、ArenaPreviewCache 缓存预览纹理、ArenaEditState/ArenaEditFrames 客户端-服务端状态和请求、ArenaManifest 资源清单、ArenaWorkArea/ArenaPastePlanner 编辑区和粘贴规划、ArenaStructureIO/clipboard bridge 结构导入导出，以及 ArenaStore/ArenaCatalog 与本地/远程资源来源相关类。

ArenaManifest 元数据模型包含 namespace/publisher/id/revision/name/author/description/tags/license/icon/colors/hidden/size/anchor/camera/stage/stats/structureHash/createdAt/updatedAt/generator/source/preview/owner/derivedFrom/contributors。ArenaEditorScreen 的页面职责能从字节码签名确认包括场地(`drawSite`)、边框/判定线(`drawFrame`)、资源信息(`drawInfo`)、贡献者(`drawContributors`)和引用/结构(`drawReference`)；包含文本草稿、延迟提交时间戳、building/pending 状态、结构导入和窗口页签/滚动交互。具体线上协议与后端能力不在 Maker 直接照搬范围内。

运行端 ArenaInstance 另有单线程 arena operation executor、异步切换、分 chunk 粘贴和 stall watchdog。此设计可作为“重结构操作不集中压在单 tick”的参考，但 Maker 世界编辑器具体采用 Fabric/Yarn/WorldEdit 可用能力需单独验证。

## 核心差距

1. **编辑体验**：Maker 主要是设置表单 + 自由搭建；缺少场景目录的卡片/结构缩略图、空间边界的稳定可视化、相机/判定面参考、编辑状态/保存进度中心。
2. **场景资源模型**：Maker 是谱面内编号场景，缺少显式尺寸、锚点、相机、判定面/边框颜色、结构哈希、预览图、来源/修订和校验统计；不能方便地把场景当作可复用资产管理。
3. **空间范围**：固定 128³ 快照让小型舞台也付出整块空间扫描成本；编辑区域与用户实际建筑边界脱离。
4. **保存一致性**：Maker 有 capture task 与元数据保存，但需要规划结构版本、原子提交、失败状态、修改后 dirty/hash 识别、重启恢复，以及保存时明确捕获区域/冲突策略。
5. **编辑/预览边界**：场景实景结构、UI 元数据、效果引用现在由不同路径操作，缺少一个以稳定 sceneId 为主键的资源服务/状态模型；索引重排潜在影响引用兼容。
6. **结构变更的 tick 压力**：创建、重置、捕获均跨大量体素；固定预算仍可在多个任务并行时叠加消耗，需要全局 tick 时间预算而非每任务独立固定预算。

## 推荐目标形态

不建议照搬示例 MOD 全套联网/贡献者/授权功能，也不建议把现有 Minecraft 方块建造替换成纯 UI 地图编辑器。建议保留 Maker 的“进入世界实际搭建”工作流，重构为三层：

### A. 场景资源与兼容层

- 以稳定 `sceneId` 为唯一内部标识，索引仅作为 UI 排序/旧版引用兼容；已有 `scene-editor:<index>` 参数继续解析，但加载时尽早转为 ID。
- 建立 `SceneManifest`（推荐 JSON 版本化而非继续扩充散落 YAML）：场景身份/名字/图标、结构文件、格式版本、显式尺寸、anchor/判定线/参考相机、preview、结构 hash、更新时间、保存状态和校验结果。
- 结构和元数据使用临时文件 + 校验 + 原子替换提交；结构文件失败时保留上一版本，不得先把 `saved=true` 写成功。
- 本地存储与 Maker 谱面/导入导出兼容接口分离。网络分享、授权、贡献者、远端商店列为未来可选扩展，不纳入首期。

### B. 场景资源管理 UI

- 场景列表以卡片展示：预览缩略图、名称、初始/特效场景标识、尺寸、已保存/未保存/保存中/失败状态、被哪些效果引用。
- 详情页按“场景信息 / 结构与边界 / 预览与坐标 / 引用 / 危险操作”分组；命名和图标即时形成 draft，但明确保存/自动保存状态，不允许点击后静默丢失。
- 动作：进入搭建、保存快照、重命名、复制场景、导入结构、导出结构、重置、删除；重置/删除需要显示影响和二次确认。
- 预览缩略图优先从结构异步生成并做有界缓存；首次无缩略图时显示简化 wireframe/空状态，不阻塞主线程。

### C. 世界内搭建与预览

- 搭建区尺寸按场景 manifest 和实际结构 bounds 控制，不固定扫描 128³；兼容旧场景时可迁移到原大小边界，或首次保存时裁切有效内容边界，但需要保留 anchor 变换和边界 padding。
- 可视化边界、中心锚点、相机视线、判定线/面、关键坐标；进入场景时显示小型 HUD：场景名、尺寸、坐标/锚点、未保存标记、保存进度、操作提示。
- 添加独立“预览模式”：锁定/虚拟相机绕场地查看，不改场景方块；编辑模式仍使用当前玩家搭建。预览模式与编辑模式明显分离，避免误操作。
- 结构粘贴/清理/捕获分批进行，所有任务共享每 tick 总处理预算或毫秒预算；工作按 chunk/section 分块，进度可取消/重试，离开/断线时保存草稿或提示未保存。

## 实施路线与优先级

### P0：先把现有系统安全化

- 做场景体素操作总预算和进度展示；按活动任务数量仲裁预算，避免重置 + 捕获同 tick 叠加。
- 记录实际非空气边界，快照只处理有效 bounds，并为旧 128³ 文件保留兼容解析。
- saved/dirty 状态来自结构 hash 或版本修订，而不是单纯文件是否存在。
- 检查压缩、磁盘写入是否位于主线程；结构编码可在纯数据快照生成后异步压缩/写临时文件，世界读取仍只在正确线程进行。

### P1：提高工作流质量

- 改造 SceneEditScreen 为场景资源浏览 + 信息详情 + 明确的保存状态；避免继续单纯添加表单按钮。
- sceneId 主键和 manifest schema version，迁移旧索引引用并验证效果 `ARENA` 绑定。
- 加入 copy/import/export 与重命名后的引用稳定性。

### P2：预览与空间工具

- 缩略图生成/缓存、世界内边界与相机/判定面预览、编辑 HUD。
- 统一相机、锚点与结构 paste origin 的坐标变换；用户可视化校准后再用于播放/导出。

### P3：验证与未来扩展

- 结构校验：尺寸超限、空结构、非法方块/实体、锚点越界、判定面遮挡、缺失结构、重复/悬空场景引用。
- 以后再考虑 arena 分类、授权、贡献者、远端素材库；不要在首期把社区服务依赖引入 Maker 本地编辑主流程。

## 深层性能建议

当前 2,097,152 block 的完整扫描成本应先优先于 UI 增强处理。理想模型为“稀疏/边界裁剪快照 + section 分块 + 预算调度 + 异步编码写盘”，同时避免重复生成和重复捕获同一场景。对每次保存记录扫描 cell 数、非空气块数、采集耗时、压缩耗时、文件体积、队列等待；用 Spark 验证保存/重置期间 MSPT，而不是仅凭进度条主观判定。

## 验收标准

- 普通小场景保存扫描量随内容 bounds 而不是固定 128³ 增长；旧 `.schem` 可导入和播放。
- 大场景生成、重置、保存期间服务器 MSPT 峰值可控，多个操作有全局调度，能显示进度/取消或安全结束。
- 新建、复制、重命名、移动排序不改变 ARENA 效果实际引用；索引迁移后旧工程兼容。
- 场景详情预览与 3D 世界结构一致，anchor/camera/judgment plane 坐标准确。
- 断线、切世界、磁盘写入失败、重复点击保存和重置时无半成品覆盖、丢失保存状态或卡死任务。
- 空场景、小尺寸、边界极值、非空气边界很稀疏、最大允许尺寸、导入未知结构版本均有覆盖。

## 证据边界

- Maker 源码确认：Owo 表单界面、玩家世界搭建、chart-scoped Scene 元数据、128³ 区域任务、分 tick 清理/捕获、`.schem` 写入和 `scene-editor:<index>` 效果引用。
- MOD JAR 确认：ArenaEditorScreen 分页及场地/边框/信息/贡献者/引用等职责；manifest 数据丰富；有预览缓存/渲染、编辑状态通信、结构/粘贴规划类；ArenaInstance 有异步切换和分块粘贴相关设计。
- 未确认：MOD 客户端 UI 的实际截图、所有后端服务行为和 Maker 当前运行时真实 MSPT；本轮不据此声称其某个 UI/性能实现一定优于 Maker 的实测值。
