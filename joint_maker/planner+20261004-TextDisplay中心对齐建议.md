# TextDisplay 中心对齐判定框修改建议

- 日期：2026-10-04
- 身份：Planner；仅源码分析与规划，不改源码、不编译、不测试、不部署。

## 直接建议

若目标判定框中心确定为 `(200.5, 67.0, -1.0)`，将 TextDisplay 的**统一世界锚点**设为该坐标，并确保特效事件相对位移为零时实体原点就在该中心：

```text
TEXT_DISPLAY_CENTER = (200.5, 67.0, -1.0)
默认 relative position = (0, 0, 0)
```

只改 `TEXT_DISPLAY_CENTER_Y: 66 -> 67` 还不够：当前普通文字默认相对偏移 `y=1.5`，所以零位移事件会被放到 `Y=68.5`。如果要沿用旧谱面默认文字视觉位置，必须有意识地迁移/保留旧的相对偏移；不要让该偏移继续隐式地被叫作“中心”。

## 当前坐标链

当前基点为 `(200.5,66,-1)`，普通 `TEXT_DISPLAY` / `HOLOGRAM` 默认相对位置为 `(0,1.5,0)`，最终实体位置为：

```text
worldPosition = baseCenter + eventPosition
```

所以默认普通文字实际位置约 `(200.5,67.5,-1)`。Text Display 的变换 translation 当前为零，scale/rotation 作用于内容变换；`displayWidth` 和 `displayHeight` 则另外按 `2*max(abs(scale))` 粗略设置。

## 推荐修改拆分（交给实现方）

1. 把中心锚点统一为可说明的判定框中心 `(200.5,67,-1)`，不要用旧文字基线代替几何中心。
2. 将普通文字默认事件 position 改为 `(0,0,0)`，或提供一次显式的兼容迁移以保持既有谱面外观；避免中心变更后多出 1.5 格偏移。
3. 检查 `TEXT_DISPLAY`、`HOLOGRAM`、`TEXT_DISPLAY_EFFECT` 三条路径是否都采用同一个锚点语义。轨道动画中的 position 应明确是“相对判定框中心”还是“相对初始实体位置”，不要混用。
4. 如果紫框是实体包围框，单独把 display width/height 设置成目标判定框宽/高；不要认为移动中心点就能解决尺寸不合。尺寸按场景左右/上下边界分别求出，不能继续用 scale 最大分量生成正方形。
5. 对现有谱面做兼容处理：默认值改变可能让既有事件上移/下移；需以旧基准加旧 position 计算旧世界坐标，再转换成相对新基准的 position，保持播放视觉不变。

## 目标坐标如何验证

- 先以游戏世界坐标确认目标青色框边界；若其左右边界为 `Xmin/Xmax`，上下边界为 `Ymin/Ymax`，前后边界为 `Zmin/Zmax`，几何中心应由各边界平均值得到。
- 用户给定中心 `(200.5,67,-1)` 可作为当前目标；但必须确认这里指的是结构开口的边界中心，还是方块占据体积的中心。
- 输出实体位置、display width/height、事件 position 与最终变换矩阵；在同一坐标系比较，不用截图像素猜偏差。
- 先校准实体中心与尺寸，再校准文字排版中心。实体中心贴合不保证文字字形像素中心贴合。

## 结论

锚点建议改成 `(200.5,67,-1)`，同时将默认相对 Y 偏移 `1.5` 归零或按旧谱面逐事件换算；紫色框是否贴合还必须另行校正 display width/height。单改中心 Y 会造成默认文字落到 `Y=68.5`，反而无法贴合。
