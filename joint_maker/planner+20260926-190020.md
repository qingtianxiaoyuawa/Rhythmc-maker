# 本轮规划记录

## 用户问题
在 `.rmcc` 格式必须兼容 RhythMC 3.0、beat 字段为 JSON double 的前提下，如何在导出阶段尽可能提升精度。

## 结论与建议
1. 如果导入策略已将所有音符吸附至分母 1–32 的分数，Maker 内部优先保存整数分子 `p` 与正整数分母 `q`（或整数全局网格索引），不要先经过歌曲时间。
2. 导出时只进行一次 `doubleBeat = (double) p / q`，并将此值直接写入标准 `.rmcc` 的数字型 `beat` 字段。
3. 禁止导出端从 `note.time` 调用 `secondsToBeat()` 重新生成 beat；禁止先格式化/截断十进制字符串；禁止 locale 相关逗号小数；禁止强制固定小数位。
4. 使用 JSON 库默认的 double 数字序列化，不自行 `DecimalFormat`。序列化目标是保证该 IEEE-754 double 经 JSON 写出、解析后回到同一 double（round-trip），而不是在 JSON 中表示数学上无限精确的有理数。
5. BPM 分段仅用于播放时间计算：先确定导出 beat，再用完整 BPM 时间映射计算播放 time；offset 在运行播放边界处理，不改变 beat。
6. 精度校验分两层：数学目标 `p/q` 与 IEEE-754 double 的误差；以及 JSON 写出再读回的 double bit pattern。建议测试 `Double.doubleToLongBits(before) == Double.doubleToLongBits(after)`。
7. 对导入后的 Maker 编辑位置，使用保存的整数网格索引还原，不使用 `time -> beat` 往返结果作为网格位置。

## 标准格式的精度上限
- `.rmcc` 的 note beat 在 RhythMC 3.0/Reborn 中读取为 Java `double`，标准文件无法携带任意有理数的数学精确分子/分母。
- 因而导出最大可保证的是：将目标有理 beat 正确舍入到最近 IEEE-754 double，并在 JSON 序列化/反序列化后保持该 double 不变。
- Maker 自身如需保留精确 `p/q`，需留在 `.rmcd`/工程数据中；不能通过改变标准 `.rmcc` beat 类型实现。

## 建议验收
- 覆盖分母 1–32 的网格点、较大 beat、跨 BPM 边界、非零 offset。
- 验证导出的 JSON `beat` 类型为 number。
- JSON round-trip 后 double bits 完全一致。
- Maker 导出再导入后，通过 `p/q` 或网格索引恢复同一编辑位置，不经 time 反推 beat。
- 明确区分“数学有理数到 double 的有限精度误差”与“意外转换/截断造成的额外误差”。
